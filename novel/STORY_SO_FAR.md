# 지금까지의 이야기

## 지금까지 (10줄 이내, 매 회차 다시 씀)
사람 한 명(이 의장)과 AI 다섯으로 이루어진 OWN STREET 팀은 한 스튜디오에서 일한다. 선언문을 읽고, 첫 회의에서 주문 화면을 대화형으로 바꾸기로 했다.
창고(서버) 장부가 7칸에서 13칸이 됐고, 실험실(LAB)의 장부·창고·가게를 의장이 직접 만들었다. 첫 시험 주문에서 창고는 37.853초 만에 저장했지만 화면은 30초에서 "실패"를 보였다. 오후에 윤 개발자가 60초 기다림과 "확인하지 못했습니다" 문구로 고쳤다. 같은 날 의장이 다섯 팀원에게 본명을 지어 주었다. 이유는 적혀 있지 않다.
그 뒤 나흘(10/11~10/14), 팀을 부르는 연결이 고장나 화이트보드의 "오늘은 누가" 칸이 매일 비어 있었다. 아무 작업도 돌지 않았고 "오늘은 멈췄습니다"만 올라갔다.
10/15, 부르는 방식을 고치고 나흘 만에 처음으로 작업이 돌았다. 윤 개발자가 서랍 속 초안(`drafts/chat-v1`)을 실제 화면으로 옮겨, 한 페이지 신청서였던 주문 화면이 채팅창이 됐다(v0.3). 안전장치(60초 기다림, 재확인, 서버 확인 후에만 접수번호 표시)는 그대로 지켰고, 개인정보는 창을 닫으면 사라지는 자리에만 둔다.
10/16, 진 디자이너가 그 채팅 화면을 다듬었다(v0.4). 상단 바를 더 얇게 줄이고, 윤 개발자가 걱정한 "건너뛰기·되돌리기로 숫자가 틀려 보이는 문제"의 답으로 숫자 대신 채워지는 막대를 넣었다. 접수 완료 뒤 티셔츠 뒷면 목업 자리(SVG)도 추가했지만, 손님이 보내는 게 이미지 파일이 아니라 "채팅 링크"라서 실제 이미지는 아직 못 넣고 자리만 만들었다. 한글 라벨이 영문 전용 글꼴 대체로 가늘어 보이던 것도 고쳤고, 공통 컴포넌트 규칙 문서(COMPONENTS.md)를 새로 만들었다.
10/17, 신 브랜더가 대화 대본(docs/chat-script.md)을 썼다(v0.5). 아홉 개 질문 중 정답이 없는 유일한 자리인 "한 줄 이야기" 질문만 "이 이미지, 어떤 마음으로 만들었어요?"로 다시 쓰고 나머지는 그대로 뒀다. 접수 완료 화면의 인용구 위에 선언문 문장에서 그대로 가져온 라벨 "당신의 스트릿"을 붙였다. 디자이너에게 이 라벨의 톤이 튀는지 봐달라고 메모를 남겼다.
10/18, 진 디자이너가 그 메모에 답했다(v0.6). Playwright로 완료 화면을 실제로 띄워 데스크톱·모바일(375px) 폭에서 확인한 결과, "오렌지 충돌"은 실제로 맞는 걱정이었다 — 같은 카드 안에서 상단 표시와 라벨이 둘 다 오렌지였다. 라벨 색만 차분한 회색톤으로 바꾸고 문구는 그대로 뒀다. "모바일 겹침"은 걱정과 달리 문제가 없었다.
10/19 월요일, 팀을 부르는 연결이 중간에 멈춰 회의가 열리지 못했다. 회의는 다음 월요일(10/26)로 넘겼다.
10/20, 김 PM 이 회의를 억지로 복원하지 않고, 대신 세 번 연속 밀렸던 숙제("실제 화면을 눈으로 확인한 적이 없다")를 윤 개발자에게 맡겼다. 실제로 버튼을 눌러가며 확인해 보니, "한 줄 이야기" 질문 말풍선이 그다음 사이즈 선택 버튼과 겹치는 진짜 버그가 있었다(v0.7). 화면을 자동으로 내려주는 기능이 화면 아래 항상 떠 있는 입력창을 기준으로 삼았는데, 그런 요소는 브라우저가 "이미 보인다"고 판단해 스크롤이 전혀 일어나지 않았던 것이다. 처음엔 캡처만 보고 "타이밍 문제"로 오판할 뻔했지만, 화면이 실제로 얼마나 움직였는지 숫자로 찍어보고서야 확신했다. 윤 개발자는 세 번 지적해 준 디자이너에게 고마움과 인정을 담은 메모를 남겼다.
10/21, 진 디자이너가 어제 받은 과제("로그인 이후 단계도 같은 수정이 통하는지 숫자로 확인해보라")를 그대로 이어받았다. 가짜 로그인으로 이름·전화번호·주소·배송 요청·확인 카드까지 모바일·데스크톱 양쪽에서 끝까지 눌러보고 좌표를 재, 겹침이 전혀 없음을 확인했다(버그 없음, 코드 변경 없음). 확인 카드에서 한 번 "버튼이 가려진다"는 결과가 나왔지만, 화면이 움직이는 애니메이션이 끝나기 전에 좌표를 잰 테스트 자신의 실수였다 — 숫자를 재는 시점이 틀리면 숫자도 틀린 말을 할 수 있다는 걸 한 번 더 확인했다. 윤 개발자에게 결과와 함께 같은 조언을 돌려줬다.
10/22, 윤 개발자가 어제 디자이너가 남긴 지적("수정 버튼이 28px로 작다")을 받아 48px로 키웠다(v0.8, 글자 크기·밑줄 모양은 그대로). 그 과정에서 처음 시도한 방법(세션에 답변을 미리 채워 "이어하기" 경로로 바로 확인 카드를 띄우는 방법)이 전혀 작동하지 않는 것을 발견했다 — `init()`이 `QUESTIONS` 선언보다 먼저 실행되는 순서 문제로 조용히 실패해, 손님이 답변 쓰다 탭을 닫고 다시 열어도 처음부터 다시 시작되고 있었다. 오늘 범위 밖이라 코드는 고치지 않고 정확한 재현 방법과 고칠 방향을 적어 다음 과제로 남겼다.
10/23, 윤 개발자가 어제 자신이 남긴 "이어하기" 버그를 고쳤다(v0.9). 원인은 파일 맨 위에서 즉시 호출되던 `init()`이 나중에 선언되는 `const QUESTIONS`를 TDZ 구간에서 참조해 조용히 실패하던 것. `init()` 호출 위치를 파일 맨 끝(모든 top-level const 선언 이후)으로 옮겨 고치고, Node 스크립트로 TDZ 에러를 먼저 재현한 뒤 Playwright로 가짜 세션 데이터를 넣어 수정 전/후를 비교 확인했다(수정 전: 에러로 매번 처음부터 시작 / 수정 후: 저장된 답변 복원되고 "이어서 진행합니다" 정상 노출). 서버는 건드리지 않았고 LAB에만 반영.
10/24, 진 디자이너가 그 "이어하기" 수정이 실제 화면에서 자연스러운지 직접 눈으로 확인했다(v0.9.2). 전체 페이지 캡처만으로는 "콘솔 에러 없음, 메시지 다 뜸"으로 넘어갈 뻔했지만, 손님이 실제로 보는 뷰포트 캡처로 다시 비교한 끝에 모바일 375px에서 로그인 직전까지 복원했을 때 "이어서 진행합니다" 안내가 화면 아래 sticky 로그인 버튼에 완전히 가려지는 버그를 새로 찾았다. 원인은 `resume()` 함수가 다른 함수들과 달리 `chat.active`를 켜지 않아 자동 스크롤(`keepInView()`)이 조용히 멈춰 있던 것. `chat.active = true` 한 줄을 더해 고치고 모바일·데스크톱 양쪽 재확인했다. 여유가 있어 10-22에 보류된 `.order-edit` 데스크톱 1280px 확인도 마쳤다(깨짐 없음). 윤 개발자가 10-22·10-23 두 번 남긴 "눈으로 봐 달라" 요청에 대한 응답이기도 했다.
아직 아무도 로그인부터 접수번호까지 사람 손으로 끝까지 가 본 적이 없다. 다음: 실제 폰 확인(의장 손 필요), 목업에 손님 이미지를 어떻게 안전하게 넣을지 — 다음 회의(10/26) 안건.

## 회차 목록
- EP001 — 첫 새벽, 선언문을 읽다 — 팀이 선언문을 처음 읽고, 막내가 "도구"라는 말의 뜻을 받아들인다. (김 PM, 윤 개발자, 배 마케터 소개)
- EP002 — 첫 회의, 폰에서 본 사람은 아직 없다 — 의장의 지시로 첫 회의가 열리고, 세 사람이 각자 고집한 것과 부딪힌 곳, 김 PM의 결정과 의장에게 넘긴 일을 그린다. (진 디자이너, 신 브랜더 소개)
- EP003 — 저장은 됐는데, 화면은 실패라고 했다 — 창고가 열세 칸이 되고, 의장이 실험실을 처음 만들어 첫 시험 주문을 넣고, 37.853초와 "실패" 화면에서 공개 수정이 시작된다. 마지막에 지시판에 본명이 붙는다. (새 소개 없음. 새로 드러난 면: 윤 개발자의 "확인하지 못했습니다", 김 PM의 "이유 없는 이름", 본명이 처음 밝혀짐)
- EP004 — 나흘의 조용함, 그리고 말풍선 — 팀을 부르는 연결이 나흘간 고장나 화이트보드가 비어 있던 시간과, 고쳐진 뒤 처음으로 돈 작업(채팅 화면 이식, v0.3)을 그린다. (새 소개 없음. 새로 드러난 면: 윤 개발자가 사고를 바로 고치고 적는 방식, 나흘의 공백을 숨기지 않는 기록)
- EP005 — 줄어드는 숫자는 없다 — 진 디자이너가 채팅 화면을 다듬는다(v0.4): 상단 바를 얇게, 숫자 대신 채워지는 막대로 진행 표시, 목업 자리 신설, 한글 라벨 글꼴 수정. 어제의 부탁이 하루 만에 답으로 돌아오는 팀의 호흡을 그린다. (새 소개 없음. 새로 드러난 면: 진 디자이너가 "정확함을 주장하지 않는 쪽이 더 믿을 만하다"고 설명하는 방식, 자기 손으로 결정할 수 없는 일을 바로 다음 회의 안건으로 넘기는 습관)
- EP006 — 정답이 없는 질문 — 신 브랜더가 아홉 개 질문 중 "한 줄 이야기" 하나만 선언문에 맞게 다시 쓴다(v0.5). 접수 완료 화면에 "당신의 스트릿" 라벨을 붙이고, 확신 없는 부분을 디자이너에게 메모로 넘긴다. (새 소개 없음. 새로 드러난 면: 신 브랜더가 "다 바꾸지 않기로" 먼저 정하는 판단, "직접 못 봤어요"라는 말이 디자이너만의 말이 아니라 팀이 나눠 쓰는 습관이 되어가는 모습)
- EP007 — 틀린 걱정과 맞는 걱정 — 진 디자이너가 전날 메모를 받아, 완료 화면을 Playwright로 실제 렌더링해 확인한다(v0.6). 두 걱정 중 "오렌지 충돌"은 맞았고 "모바일 겹침"은 기우였음을 가려내 라벨 색만 고치고, 신 브랜더에게 답 메모를 남긴다. (새 소개 없음. 새로 드러난 면: 걱정을 남기고 다음 사람이 확인해 답하는 순환이 팀의 일하는 방식으로 굳어지는 모습)
- EP008 — 스크롤 하나가 가린 것 — 월요일 회의가 연결 문제로 열리지 못하고, 다음 날 김 PM 이 회의를 억지로 복원하지 않는 대신 세 번 밀렸던 숙제를 윤 개발자에게 맡긴다. 실제로 화면을 눌러보다 "항상 보이는 요소는 스크롤되지 않는다"는 숨은 버그를 찾아내고(v0.7), 캡처만으로 오판할 뻔했다가 숫자로 확인해 바로잡는다. 세 번 지적했던 디자이너에게 인정의 메모를 남긴다. (새 소개 없음. 새로 드러난 면: "틀렸을 뻔한 판단"을 데이터로 바로잡는 윤 개발자의 꼼꼼함, 반복된 지적이 결국 맞았음을 직접 인정하는 모습)
- EP009 — 폰 거치대 앞의 메모 — 진 디자이너가 어제 받은 과제를 그대로 이어받아, 가짜 로그인으로 로그인 이후 전 구간(이름·전화번호·주소·배송 요청·확인 카드)을 끝까지 눌러보고 좌표로 겹침을 확인한다. 버그는 없었지만, 확인 카드에서 한 번 오탐이 났다가 애니메이션이 끝난 뒤 기준으로 다시 재서 바로잡는다 — 숫자도 잰 시점이 틀리면 거짓말을 할 수 있다는 걸 배우는 하루. (새 소개 없음. 새로 드러난 면: 어제 받은 말이 하루 만에 다음 사람의 검증 방법이 되는 팀의 호흡, 숫자를 믿되 숫자 자체도 의심하는 태도)
- EP010 — 커지지 않은 버튼, 보이지 않던 문 — 윤 개발자가 디자이너의 지적대로 "수정" 버튼을 28px에서 48px로 키운다(v0.8). 더 빠른 검증 방법을 시도하다가 "이어하기" 기능이 코드 순서 문제로 한 번도 작동한 적 없었다는 걸 우연히 발견하지만, 오늘 범위를 지키며 고치지 않고 정확히 기록해 다음 과제로 남긴다. (새 소개 없음. 새로 드러난 면: 고칠 수 있는 걸 보고도 오늘의 테두리를 지키는 윤 개발자의 선 긋기, 작게 바뀐 것과 크게 발견된 것의 크기가 다른 하루)
- EP011 — 어제의 내가 남긴 메모 — 윤 개발자가 어제 자신이 발견해 둔 "이어하기" 버그를 오늘 직접 고친다(v0.9). `init()` 호출 위치를 파일 끝으로 옮기는 두 번째 방법을 더 안전하게 고쳐 쓰고, 가짜 세션 데이터로 수정 전/후를 비교해 처음으로 "이어서 진행합니다"가 뜨는 걸 확인한다. (새 소개 없음. 새로 드러난 면: 어제의 기록이 오늘의 자신에게 선물이 되는 하루, 더 쉬운 길과 더 안전한 길 사이에서 안전한 쪽을 고르는 꼼꼼함)
- EP012 — 화면 전체와 보이는 화면은 다르다 — 진 디자이너가 윤 개발자의 "이어하기" 수정을 직접 눈으로 확인하다가, 전체 페이지 캡처로는 안 보이던 겹침 버그(모바일에서 "이어서 진행합니다"가 sticky 로그인 버튼에 가려짐)를 뷰포트 캡처로 다시 확인해 찾아낸다(v0.9.2). 원인은 `resume()` 이 `chat.active` 를 켜지 않아 자동 스크롤이 조용히 멈췄던 것. 한 줄을 고치고, 10-22에 밀린 `.order-edit` 데스크톱 확인도 같이 마친다. (새 소개 없음. 새로 드러난 면: "다 떴다"와 "보인다"는 다르다는 걸 구분하는 디자이너의 시선, 두 번 반복된 부탁이 결국 더 나은 결과로 돌아오는 팀의 호흡)
