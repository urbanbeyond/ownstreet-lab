# developer 의 의견

(2026-10-08, 맨 첫 회의. 두 번째 발언자. 먼저 쓴 진 디자이너의 의견을 읽고 썼다.)

읽은 것: `app/app.js` 전체, `app/config.js`, `app/index.html` (폼과 안내 부분), `backend/Code.gs` 전체, `drafts/chat-v1/` 의 README, app.js 전체, index.html 전체, styles.css 의 채팅 레이아웃 부분, `.github/workflows` 의 파일 목록과 LAB/LIVE 관련 줄.
실행한 것: `node --check` 로 `app/app.js`, `app/config.js`, `drafts/chat-v1/app.js` 문법 확인 (셋 다 통과). 초안 app.js 가 찾는 요소 id 가 초안 index.html 에 모두 있는지 비교 (빠진 것 없음. `chatText` 는 코드가 나중에 만든다).
못 한 것: 폰이나 브라우저에서 띄워 보지 못했다. 인스타·카카오 인앱 브라우저는 실제로 열어 보지 못했다. Apps Script 서버에 요청을 보내 보지 않았다 (보낼 수도, 보내서도 안 된다). 아래는 코드를 읽고 한 판단이다.

## 안건에 대한 내 입장: 찬성. 단, 서버가 먼저다

한 페이지 폼을 대화형으로 바꾸는 것에 찬성한다. 이유는 두 가지다.
1. v0 폼은 받는 정보가 이름, 전화번호, URL 뿐이다. 사이즈와 주소를 받지 않으니 접수만으로는 제작·배송을 시작할 수 없다. 칸이 5~6개로 늘어나는 순간 한 페이지 폼은 길어지고, 한 번에 한 질문씩 묻는 쪽이 폰에서 낫다.
2. 선언문이 말하는 "손님이 직접 손댄다"는 질문을 하나씩 주고받을 때 더 잘 담긴다. 지금 질문이 배송 정보 위주라는 한계는 디자이너와 같은 생각이다.

반대 조건은 하나다. 서버를 고치기 전에 화면을 LIVE 로 올리면 안 된다. 아래 "서버" 부분에 이유를 썼다.

## 지금 서비스(v0)를 개발자 눈으로 평가

**잘 만들어진 것 (건드리지 말고 초안도 이어받아야 하는 것)**
- 접수번호는 서버가 시트에 쓰고 다시 읽어 확인한 뒤에만 나간다 (`Code.gs` 115~119행). 화면은 `ok === true` 와 `OS-숫자` 형식이 둘 다 맞을 때만 완료를 보여 준다 (`app.js` 356행). 거짓 성공을 막는 두 겹이다.
- 재시도할 때 같은 `clientRef` 를 다시 보낸다. 30초 안에 응답이 없어 손님이 다시 눌러도 서버가 같은 번호를 돌려준다 (`Code.gs` 95~99행).
- 로그인 토큰이 만료되면 새로 받아 한 번 더 시도한다 (`app.js` 304~307행).
- 전화번호와 URL 검증 규칙이 화면과 서버에서 같다. 시트 수식 주입도 막는다 (`safeCell_`).

**고쳐야 할 것**
1. **중복 방지가 영구적이지 않다.** 같은 요청인지 알아보는 기록이 `CacheService` 에만 있다 (`Code.gs` 94~98행). 캐시는 사라질 수 있고, 시트에는 `clientRef` 가 없다. 저장은 됐는데 읽어서 확인하는 단계에서 오류가 나면 행은 남고 손님은 실패를 보고, 다시 누르면 행이 하나 더 생긴다. 서버가 `clientRef` 를 시트에 저장하고 그걸로 찾아야 한다.
2. **서버가 저장하는 항목이 7칸뿐이다.** 접수번호, 접수시간, 이메일, 이름, 전화번호, URL, 상태 (`Code.gs` 33행). 사이즈, 주소, 요청사항은 없다. 개인정보 동의를 받았다는 기록(언제, 어떤 문구 버전)도 저장하지 않는다. `consent === true` 인지만 확인하고 버린다 (85행).
3. **URL 은 형식만 본다.** 공개 링크인지, 이미지가 있는 페이지인지, PNG 인지는 아무도 확인하지 않는다 (`cleanUrl_`). 안내문에는 "PNG Only" 라고 쓰여 있지만 폼은 그걸 묻지도 않는다. 서버가 링크를 열어 확인할 수는 있지만 (`UrlFetchApp`) PNG 인지는 알 수 없다. 이 점은 아직 방법이 없다고 솔직히 적는다.
4. **스프레드시트 ID 를 배포할 때마다 손으로 코드에 붙여넣는다.** 공개 저장소라 `SPREADSHEET_ID` 가 비어 있다 (`Code.gs` 28행). 의장이 전체 코드를 복사해 붙이면 ID 가 지워진다. 독립 스크립트라면 저장이 `SERVER_ERROR` 로 끝난다. 규칙대로 Script Properties 에서 읽게 바꿔야 한다. (`FIREBASE_API_KEY` 는 Firebase 웹 키라서 `config.js` 에도 공개된 값이다. 비밀값이 아니라서 옮기지 않아도 된다고 본다.)
5. **실패 안내가 뭉뚱그려져 있다.** 서버가 `BUSY`, `NOT_CONFIGURED`, `AUTH_UNAVAILABLE` 을 돌려줘도 화면은 "잠시 후 다시 시도" 하나로 보여 준다 (`app.js` 378~385행). 손님에게는 괜찮지만 우리가 어디서 막혔는지 알 방법이 콘솔뿐이다.
6. **손님이 어디서 그만두는지 우리는 모른다.** `app/` 과 초안 어디에서도 단계별 기록 코드를 찾지 못했다. 대화형으로 바꿔도 좋아졌는지 알 수 없다.
7. **주문 후에 손님이 번호를 잃어버리면 확인할 방법이 없다.** 완료 창을 닫으면 끝이다. 시트에는 `상태` 열이 있지만 손님은 못 본다.

## 초안(chat-v1)을 개발자 눈으로 평가

**잘한 것**
- 완료 조건이 v0 와 같다 (`handleResult`, 617행). 서버 확인과 접수번호 형식을 모두 통과해야만 완료 말풍선이 나온다. 임의 번호를 만드는 코드는 보이지 않는다.
- 이전 확인 카드를 `retireCards` 로 비활성화한다. 예전 카드의 "주문하기"를 다시 눌러 두 번 접수하는 일을 막는다.
- 저장된 임시 값을 다시 검사하고, 앞에서부터 올바른 항목까지만 쓴다 (`loadDraft`).
- `submitOrder` 는 `chat.busy` 로 이중 클릭을 막고, 서버 확인이 실패하면 "다시 시도 / 내용 수정 / 카톡 문의"를 준다.
- 문법은 통과했고 id 누락도 없다.

**서버와 맞물리지 않는 것**
- 초안은 접수 전에 GET 으로 `info.version >= 2` 를 확인한다 (`ensureServer`, 559행). 지금 `doGet` 은 `version` 을 돌려주지 않는다 (`Code.gs` 57~64행). 그래서 현재 서버에서는 모든 주문이 `NOT_READY` 로 끝난다. 디자이너의 판단에 동의한다.
- 서버를 고쳐야 할 것은 다섯 가지다.
  1. `doGet` 이 `version: 2` 를 돌려준다.
  2. `handleRequest_` 가 `size`, `address`, `memo` 를 받고 검증한다. 사이즈는 S, M, L, XL, 2XL, 3XL 중 하나여야 한다. 서버는 `config.js` 를 읽지 못해서 목록을 코드에 한 번 더 적어야 한다. 사이즈표가 바뀌면 두 군데를 고쳐야 한다는 단점을 안고 간다.
  3. 시트에 열을 **상태 열 뒤에 덧붙인다** (사이즈, 주소, 요청사항, clientRef, 동의 시각 등). 기존 열의 순서를 바꾸면 의장이 이미 쓰는 시트가 어긋난다. 이미 헤더가 있는 시트에도 새 헤더를 채우는 코드가 필요하다. 지금 `getSheet_` 는 시트가 비었을 때만 헤더를 쓴다 (178행).
  4. `address`, `memo` 에도 `safeCell_` 을 적용한다.
  5. 응답에 `v: 2` 를 넣는다 (다음 항목에서 이유를 설명한다).

**가짜 성공이 생길 틈**
- 가장 큰 틈은 서버 버전이 어긋났을 때다. 초안의 POST 본문에는 `v: 2` 가 있지만, 옛 서버는 모르는 항목을 조용히 버리고 `ok: true` 와 접수번호를 돌려준다. 그러면 사이즈와 주소가 저장되지 않았는데 손님은 "접수됐습니다"를 본다. 지금은 사전 GET 확인이 이 틈을 막는다. 하지만 GET 과 POST 사이의 짧은 틈이고, 세션 동안 `serverOk` 를 한 번만 확인하고 기억한다 (550행). 막는 장치가 하나뿐이다.
  - 제안: 새 서버가 성공 응답에 `v: 2` 를 넣고, 화면은 `r.v >= 2` 일 때만 완료로 본다. 응답이 증거가 되게 한다.
- 새로고침과 `clientRef`. `state.pending` 은 메모리에만 있다. 접수 요청을 보낸 직후 탭이 닫히거나 새로고침되면, 임시 저장에는 `clientRef` 가 없어서 (초안 `saveDraft` 는 `chat.data` 만 저장한다) 다시 접수할 때 새 `clientRef` 가 만들어진다. 서버는 같은 요청이라고 알아보지 못하고 행이 하나 더 생긴다. 임시 저장에 `clientRef` 를 함께 넣어야 한다. 그 사이 서버에 이미 저장됐을 수 있기 때문이다. 지금 서버의 캐시 중복 방지는 6시간이므로, 위 1번 항목(시트에 `clientRef` 저장)과 같이 가야 안전하다.
- `CONSENT_REQUIRED` 응답을 초안은 따로 처리하지 않고 일반 실패로 보여 준다. 화면이 항상 `true` 를 보내기 때문에 실제로는 거의 안 나온다. 작은 일이다.

**중간에 나갔다 돌아온 손님**
- 같은 폰의 같은 브라우저에서는 이어진다. 답을 하나 할 때마다 `localStorage` 에 7일간 저장하고, 돌아오면 대화를 다시 그려 주고 "이어서 진행합니다"를 보여 준다. 동의 체크는 저장하지 않아서 다시 받는다. 좋은 설계다.
- 문제 두 가지.
  1. **개인정보가 폰에 평문으로 7일 남는다.** 이름, 전화번호, 주소다. 로그아웃해도 지워지지 않는다 (`logout()` 은 `clearDraft()` 를 부르지 않는다). 가족이나 친구와 같이 쓰는 폰이면 문제가 된다. 내 제안은 임시 저장을 이미지 링크와 사이즈까지만 하고, 이름·전화번호·주소는 `sessionStorage` 로 (탭을 닫으면 사라지게) 하거나 아예 저장하지 않는 것이다. 편의와 개인정보의 균형이라서 의장이 봐 주면 좋겠다.
  2. **인스타에서 열었다가 외부 브라우저로 옮기면 이어지지 않는다.** `localStorage` 는 브라우저마다 따로이기 때문이다. 이게 아래 인앱 브라우저 문제와 이어진다.

**인앱 브라우저(인스타, 카카오톡)**
- 초안은 인앱 브라우저를 `isInAppBrowser()` 로 알아보고 (v0 와 같은 판별식), 대화 시작 버튼을 없애고 "Chrome이나 Safari에서 열어주세요" 와 "브라우저로 열기 / 주소 복사" 를 준다. 카카오톡은 `kakaotalk://web/openExternal`, 안드로이드는 `intent://` 로 열고, iOS 는 손으로 안내한다. 코드는 읽었지만 **실제 앱에서 눌러 보지 못했다.** 이 열기 버튼이 정말 작동하는지는 확인하지 못했다.
- 초안의 구조적 문제는 로그인이 마지막 단계라는 것이다. 질문 6개에 답한 뒤에 Google 팝업이 뜬다. 팝업이 막히는 환경이면 손님은 마지막에서 막힌다. 인앱 손님은 입장하자마자 막히므로 피해가 적다. 그 밖에 팝업 차단이나 취소가 문제다.
- Firebase 로드가 늦거나 실패할 때도 문제가 있다. 초안은 `setupAuth()` 를 기다리지 않고 바로 `initChat()` 을 부른다 (47행). 그래서 `unavailable` 안내(305행)는 Firebase 설정값이 비어 있는 경우에만 채팅에 나온다. 라이브러리 로드에 실패하면 채팅은 이미 "주문 시작" 버튼을 보여 주고 있고, 실패 안내는 위쪽 hero 에만 뜬다. 손님은 질문에 다 답한 뒤 "지금은 로그인을 준비하고 있습니다" 를 본다. 직접 실행해 보지는 않았다. 코드 순서를 읽고 한 판단이다.

**디자이너와 겹치는 부분 (동의)**
- 입력창이 문서 흐름 안에 있고 고정되어 있지 않다. 초안 `styles.css` 에서 `.chat-input` 은 `margin-top: 16px; min-height: 52px` 뿐이고, 채팅 레이아웃에는 `position: fixed/sticky` 나 `100dvh` 가 없다. 확인했다. 폰에서 어떻게 보이는지는 못 봤다.
- "배송비 포함" 문구는 `config.js`, `CLAUDE.md` 어디에도 근거가 없다. v0 는 주소를 받지 않았으니 배송을 어떻게 했는지도 기록으로는 확인하지 못했다. 의장이 확인해 줘야 한다.
- `privacyRetention` 이 비어 있다. 주소를 새로 받으면 이 빈칸은 더 이상 미룰 수 없다.

## 이번 주 제안 3개

개발 순서는 **서버 먼저, 화면 다음, LIVE 는 맨 마지막** 이다.

1. **Code.gs v2 를 옛 형식과 함께 받도록 (하위 호환) 만든다. 하루 분량. 의장 손이 필요하다 (LAB 에 배포).**
   - 무엇: `doGet` 에 `version: 2`. 요청에 `size`, `address`, `memo` 가 있으면 검증해서 저장. 시트 열은 상태 열 뒤에 덧붙이고 헤더가 없는 기존 시트에도 채운다. `clientRef` 를 시트에 저장해서 중복을 찾는다. 동의 시각을 저장한다. 성공 응답에 `v: 2`. `SPREADSHEET_ID` 는 Script Properties 에서 읽는다. 주문 데이터 형식은 `backend/API.md` 로 문서화한다.
   - 왜 하위 호환인가: 지금 LIVE 서버는 v0 폼이 쓰고 있다. 새 서버가 `v: 2` 가 없는 요청(옛 형식)도 그대로 받으면, 의장이 LIVE 서버를 먼저 바꿔도 지금 손님은 아무 영향이 없다. 반대로 화면이 먼저 LIVE 에 올라가면 서버가 아직 옛것이라 모든 주문이 막힌다. 서버를 먼저, 호환되게 올리는 이유다.
   - 의장 손: `OPERATOR_TODO.md` 에 "LAB Apps Script 에 Code.gs 반영 → 확인 후 LIVE 반영" 을 적는다. LAB 스크립트의 Script Properties 에 시트 ID 를 한 번 넣어야 한다. 확인은 LAB 주소를 브라우저로 열어 `version` 이 2 로 나오는지 보는 것으로 충분하다 (고객 데이터는 나오지 않는다).
   - 배포 전까지는 LAB 화면이 새 기능을 쓰지 못한다. 기다림도 기록으로 남긴다.

2. **초안을 `app/` 으로 옮겨 다듬는다. 하루 분량. 의장 손 필요 없음. 1번과 같은 날 하거나 다음 날.** 서버 배포를 기다리는 동안 해도 된다. 이 화면은 서버가 v2 가 되기 전에는 LAB 에서 "지금은 주문을 준비하고 있습니다"를 보여 주는데, 이것은 의도한 안전장치다.
   - 고칠 것 (내가 개발자로서): ① 임시 저장에 `clientRef` 포함. ② 성공 응답의 `v >= 2` 확인. ③ 로그아웃과 "처음부터 다시"에서 임시 저장 삭제. 개인 정보 저장 범위 줄이기. ④ Firebase 로드 실패가 채팅 안에서 바로 보이게 `initChat` 을 `setupAuth` 뒤에 부르기. ⑤ 로그인 위치 (아래). ⑥ 서버 실패 코드별 문구 (`BUSY`, `CONSENT_REQUIRED` 포함).
   - **로그인 위치 제안**: 이미지 링크 → 사이즈 → **로그인** → 이름 → 전화번호 → 주소 → 요청사항 → 확인. 이유: 가장 재미있는 부분(내 이미지, 내 사이즈)을 먼저 하고, 개인정보를 치기 전에 로그인 문제(팝업 차단, 취소)를 만난다. 지금 초안은 맨 끝이라서 막히면 6개 답이 아깝다. 반대 의견도 안다. 맨 앞 로그인은 처음 오는 사람에게 부담이 된다. 이 선택이 더 나은지 우리는 데이터가 없다 (단계별 기록이 없다). 이름 질문에서는 Google 계정 이름을 버튼으로 제안하되, 손님이 직접 고르게 한다.
   - 디자이너의 "진짜 채팅 화면(100dvh, 고정 입력창)" 작업과 같은 파일(`app.js` 의 `setTextInput`, `setChoices`, `keepInView`)을 건드린다. 같은 날 둘이 만지면 충돌하므로, 내가 로직을 먼저 `app/` 에 올린 다음 디자이너가 레이아웃을 입히는 순서가 안전하다.

3. **LAB 에서 실제 한 건 주문해 보고 LIVE 순서를 정한다. 반나절. 의장 손이 필요하다 (테스트 주문, LIVE 서버 배포, LIVE 반영 버튼).**
   - 의장이 LAB 에서 테스트 주문 한 건을 넣고 (LAB 은 별도 시트다), 접수번호가 나오고 시트에 사이즈·주소가 들어갔는지 눈으로 확인한다. 결제 링크와 QR 이 LAB 에서 막혀 있는지도 본다. 저는 고객 시트에 접근하지 않으므로 이 확인은 의장 몫이다.
   - 통과하면 순서는 ① LIVE 의 Apps Script 에 Code.gs 반영 (하위 호환이라 v0 손님에게 영향 없음) ② LIVE 시트에도 새 열이 생겼는지 확인 ③ 그다음에 LIVE 반영 버튼. ①보다 ③이 먼저면 실제 손님이 주문하지 못한다.
   - **서버 배포 없이 되는 길도 생각해 봤다.** 이름 필드에 사이즈와 주소를 함께 담아 보내는 식의 꼼수는 하지 않는다. 검증이 깨지고 데이터가 지저분해진다. 정직한 대안은 하나다. 대화형 화면을 지금 서버에 맞춰 **이미지 링크 → 이름 → 전화번호** 3문항만 묻는 것으로 먼저 LIVE 에 올리고, 사이즈와 주소는 접수 후 카카오톡 채널에서 받는 것이다. 의장이 서버 배포를 며칠 못 한다면 이 길이 있다. 다만 그러면 대화형의 장점 (사이즈, 주소를 화면에서 받는 것) 이 빠지므로 1번을 권한다.

## 의장의 선언문(OWN_STREET_LIFE.md)에 비추어, 내 분야에서 가장 먼저 다가갈 수 있는 것 한 가지

**손님의 말이 서버에 그대로 남는 것.** 선언문이 말하는 "내 생각이 담긴 걸 내가 누린다"를 개발자가 할 수 있는 가장 작은 모양은, 손님이 쓴 문장을 접수 데이터에 한 칸으로 보관하고 그 손님의 완료 화면에 되돌려 보여 주는 것이다. 요청사항 칸이 이미 있으니, 질문 문구를 "요청사항이 있으면"에서 "이 이미지에 담긴 생각을 한 줄로 적어 주세요(건너뛰어도 돼요)"로 바꾸는 것도 서버 변경 없이 할 수 있다. AI 가 정해 주는 것이 아니라 손님이 직접 쓰는 문장이다. 단, 이 문구는 의장의 선언문을 해석하는 일이므로 의장이 보고 정하면 좋겠다.

## 플랫폼까지 가려면 내 분야에서 결국 필요한 것 한 가지

**손님 단위로 데이터를 가진 저장소와 "내 주문 조회".** 지금 서버는 스프레드시트에 이메일을 한 열로 적을 뿐이다. 손님이 자기 주문과 상태를 다시 볼 수 없고, 신 브랜더가 만들 "내 브랜드"(이름, 로고, 무드)를 손님 계정에 붙일 곳도 없다. 시트를 데이터베이스처럼 쓰는 방식은 접수번호를 만들 때마다 번호 열 전체를 읽는 구조라서 (`nextSequence_`) 규모가 커지면 느려진다. 당장은 로그인한 손님의 주문만 돌려주는 `myOrders` 기능을 서버에 추가하는 것이 첫걸음이다. 그다음에 손님 계정에 붙는 저장소를 정해야 한다. 이미 Firebase 프로젝트가 있으니 그 안의 데이터베이스가 후보지만, 그 기능이 켜져 있는지는 확인하지 못했다. 선택은 비용(유료 API 금지 원칙)과 의장의 결정이 필요하다. 이번 주 제안에는 넣지 않고 방향으로만 남긴다.
