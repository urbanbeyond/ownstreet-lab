# developer 의 의견 (정기 회의, 2026-11-24 화요일)

진 디자이너 의견을 먼저 읽었다. 코드는 고치지 않았다. `app/app.js`, `app/COMPONENTS.md`, `app/naming-words.js` 머리말, `docs/naegabrand/example-chair.md`, R-035~R-043, `records/2026-11-19/notes.md`, 지난 회의(11-17) 내 의견을 읽고 쓴다. 의장 본인 예시는 `example-chair.md` 에 의장이 직접 적어 준 것만 인용하고, 그 밖의 내용은 지어내지 않는다.

## 지금 서비스에서 내 눈에 가장 걸리는 것

1. **예시가 코드 안에 박혀 있다.** `app/app.js` 에 `WORD_EXAMPLES`(단어 8개)와 `CLUES`(질문 8개 + 의장 답)가 배열로 직접 들어 있다. 예시를 하나 늘리려면 코드 파일을 고쳐야 하고, 신 브랜더가 글만 고치고 싶어도 못 한다. 게다가 원천 기획(02 문서 3장)은 "웹과 카카오 챗봇이 같은 글 데이터를 가져다 쓴다"고 했는데, 지금 예시는 웹 안에만 있다. 같은 내용이 두 군데로 갈라질 구조다.
2. **예시 단어가 이름 사전과 이어지는지 아무도 확인하지 않는다.** `WORD_EXAMPLES` 의 단어를 눌러 시작해도 03 이름 단계에서 `naming-words.js` 에 그 단어가 없으면 "내 AI 에게 물어볼 글"로 빠진다. 예시로 시작한 사람이 가장 먼저 "사전에 없음"을 만나면 가벼운 시작이 거기서 꺾인다. 8개 단어가 지금 전부 사전에 걸리는지는 내가 이번 회의에서 코드를 돌려 확인하지 않았다(회의 모드라 실행하지 않음). 걸리는지는 목요일에 확인해야 할 일이고, 지금은 "확인하는 장치가 없다"가 걸리는 것이다.

## 이번 주 제안 3개

1. **예시를 글 데이터 한 파일로 뺀다 — `docs/naegabrand/examples.json` 을 원본으로, 웹은 같은 내용을 `app/examples.js` 로 읽는다.**
   - 무엇을: 카드 한 장의 구조를 아래처럼 고정한다. 디자이너가 요청한 필드(시작 단어·한 줄 이유·누구·가상 여부)를 모두 포함하고, 의장 카드의 "자리" 상태도 표현한다.
     ```
     { "id": "chair-1",
       "who": "chair" | "fictional",
       "fictional": false | true,          // 화면의 '가상' 꼬리표는 이 값으로만 붙는다
       "status": "ready" | "pending",       // pending 이면 내용 필드는 null
       "word": "다정하다",
       "reason": "떠오른 기억",             // 공백 포함 30자 안팎(디자이너 추정, 렌더 확인 전)
       "journey": [ {"step": 1, "text": "..."} ],   // 선택. 처음부터 끝까지 따라간 예시용
       "source": "example-chair.md ⑥"      // 의장 카드는 어디서 받은 말인지 필수
     }
     ```
   - 규칙(검증 스크립트가 어기면 실패): ① `who:"fictional"` 이면 `fictional:true` 필수 ② `who:"chair"` 이고 `ready` 이면 `source` 필수 — 의장이 준 문서가 가리켜지지 않으면 못 올린다 ③ `pending` 카드의 `word`·`reason`·`journey` 는 `null`(지어낸 내용이 들어갈 자리를 구조로 막는다) ④ 모든 `word` 는 `naming-words.js` 에 걸려야 한다(위 걸림 2번). 그리고 `CLUES`·`WORD_EXAMPLES` 도 같은 파일의 `clues`·`startWords` 칸으로 옮긴다.
   - 왜: 글은 신 브랜더, 화면은 디자이너, 연결은 내가 맡는 분업이 된다. 카카오 챗봇도 같은 JSON 을 읽을 수 있다.
   - 솔직한 한계: Netlify 는 `app/` 만 올리므로 `docs/` 의 JSON 을 웹이 직접 읽지 못한다. 그래서 원본과 `app/examples.js` 두 벌이 생긴다. 둘을 같게 만드는 작은 node 스크립트(`scripts/` 에 둔다, 서버·유료 API 없음)를 같이 만들고, 다르면 실패하게 한다. 서버 배포는 필요 없다.
   - 분량: 하루(목요일). 의장 손은 필요 없음. 단, 신 브랜더가 가상 인물 카드 글을 채우는 일이 먼저 또는 같이 와야 한다.

2. **"시작 도우미"의 동작을 정한다 — 상태를 만들지 않고, 사용자 입력은 입력창에만.**
   - 무엇을: 카드의 "이 카드로 시작"을 누르면 `#wordInput` 에 단어를 채우고 포커스를 둔다(지금 칩 `WORD_EXAMPLES` 와 같은 동작). 사용자가 고치지 않고 그대로 가도 막지 않는다. "아무 단어도 안 떠올라" 시트(디자이너 제안 2)는 `clues` 를 섞은 순서로 한 번에 하나씩, 같은 질문이 연달아 안 나오게 돌리고, 마지막까지 가면 처음으로 돌아간다. 사용자가 시트에 쓴 답은 단어 칸에만 들어가고 따로 저장하지 않는다.
   - 하나 더: `state` 에 `fromExample`(예시 id)을 저장할지 결정이 필요하다. 나는 **저장하지 않는 쪽**을 제안한다. 이 기기에만 저장되는 것이라 개인정보 문제는 없지만, 그 값을 어디에도 쓰지 않으면 넣을 이유가 없다. 나중에 "예시로 시작한 사람이 끝까지 갔는지"를 알고 싶어지면 그때 의장 결정과 함께 넣는다(11-17 회의의 funnel ping 논의와 같은 결).
   - 왜: R-037 "정말 가볍게" 를 코드로 지키려면 걸음이 늘어나는 기능을 넣지 않는 게 안전하다. 새 화면 단계를 만들지 않고 01 안에서 끝낸다(02 문서 ① 규칙).
   - 분량: 제안 1 과 같은 날, 또는 반나절 추가. 의장 손 필요 없음.

3. **카드 데이터의 오류를 화면이 조용히 삼키지 않게 한다 — 데이터가 깨지면 예시 줄만 숨기고 입력창은 그대로 살린다.**
   - 무엇을: 예시 줄이 비었거나 형식이 틀려도 01 의 입력창·"다음" 버튼은 항상 동작해야 한다. 카드를 그리다 오류가 나면 카드 줄만 숨긴다. 가짜 카드를 대신 채우지 않는다(R-034 이후에도 "가짜로 채우지 않는다"는 이 팀의 원칙).
   - 왜: 예시는 보조다. 보조가 본 흐름을 막으면 안 된다.
   - 분량: 제안 1 안에 포함. 반나절 미만.

## 다른 팀원 의견에 대해

**진 디자이너 의견에 대부분 동의한다.** 요청한 필드 구조는 위 제안 1 에 그대로 넣었다. 다만 다섯 가지를 분명히 한다.

- **동의: 카드는 데이터에서 읽고, 가상 여부 필드가 있어야 한다.** 필드가 없으면 화면이 가상 꼬리표를 붙일 근거가 없다. 위 규칙 ①이 이를 강제한다.
- **동의: "막혔어?"를 눈에 띄게.** 구현은 어렵지 않다. 다만 문구는 디자이너와 신 브랜더가 정해 주면 따른다.
- **일부 반대: 의장 카드 "자리"를 사용자 화면에 점선 카드로 내보내는 것.** 아직 내용이 없는 카드를 손님이 보면 "미완성" 인상이 들 수 있다(의장이 R-040 에서 "촌스럽다, 떠나가겠다"고 한 결). 제안은, 구조에서 `pending` 상태는 만들되 **화면은 기본적으로 pending 카드를 그리지 않고**, 의장이 내용을 주면 그때 나타나게 하는 것이다. 자리를 보여 줄지는 디자이너·PM 이 정하면 따른다. 이건 내 의견이고 의장 결정 사항은 아니다.
- **한 가지 사실 확인: 의장 카드가 완전히 빈 것은 아니다.** `example-chair.md` 에는 의장이 직접 고른 ⑥ "다정하다"와 "한 번 더: 떠오른 기억"이 이미 있다. 이 두 줄은 지어낸 것이 아니라 의장이 준 것이므로 카드 한 장의 `word`·`reason` 에 쓸 수 있다(`source` 로 그 위치를 적는다). 하지만 이름·로고·이후 여정은 의장이 준 적이 없으므로 `journey` 는 `null` 로 둔다. 1기 현장에서 효과가 있었다는 "만든 과정과 결과물 공유"의 알맹이는 아직 의장이 줄 때까지 비어 있다.
- **디자이너의 30자 한도는 추정이고 렌더 확인 전이라고 했다 — 나도 같다.** 검증 스크립트의 한도(글자 수)는 숫자만 바꾸면 되게 한 곳에 두겠다. 한글은 한 글자가 영문보다 넓어서 폭이 좁을 때 줄바꿈이 생길 수 있다. 실제 폰 확인(B4)을 거치기 전까지는 한 줄이라고 확정하지 않는다.
- **디자이너 제안 3(03 더 보기)에 대해:** 이름 후보 수가 늘어날 때 "처음 3개만"은 구현이 간단하다(배열 slice + 버튼). 다만 `namingIdeas` 가 돌려주는 순서가 "좋은 것부터"가 아니라 사전에 적힌 순서이므로, 앞의 3개가 가장 좋은 3개라는 보장이 없다. 신 브랜더가 갈래마다 제일 쓸 만한 것을 앞에 두어야 이 제안이 의미가 있다. 이건 신 브랜더에게 걸어 둔다.

## 의장의 선언문(OWN_STREET_LIFE.md)에 비추어, 내 분야에서 가장 먼저 다가갈 수 있는 것

**예시를 "정답"이 아니라 "출발점"으로만 작동하게 만드는 것.** 선언문의 "추천은 출발점일 뿐이고 마지막 선택은 사용자가 한다"를 코드에서 지키는 방법은 단순하다. 예시를 눌렀을 때 결과가 확정 값이 되지 않고 **고칠 수 있는 입력창에 글자로만 들어가게** 하는 것이다. 이 원칙은 내가 이번 주에 바로 지킬 수 있고, 제안 2 가 그 구현이다.

## 플랫폼까지 가려면 내 분야에서 결국 필요한 것

**저장 순간에만 붙는 로그인과 "내 브랜드 모음" 저장소.** R-042 에서 의장이 정한 대로 로그인은 "내 브랜드 저장" 순간에 붙는다. 그때 서버에서 필요한 것은 로그인 토큰 검증과, 사용자별로 브랜드 여러 개를 저장·조회하는 일이다(지금 `naegabrand:v1` 은 한 개짜리, 이 기기 한정). 이건 `Code.gs` 배포나 새 저장소 결정이 따르므로 의장 손이 필요하고, 지금 당장 할 일은 아니다. 지금 할 수 있는 준비는 하나다: 예시 카드와 사용자의 저장 데이터가 같은 필드 이름(`word` 등)을 쓰게 해서, 나중에 "내 브랜드"도 같은 틀로 옮겨 담을 수 있게 하는 것. 이번에 만들 `examples.json` 의 필드 이름을 정할 때 그걸 감안하겠다. 방향만 적는다. 일정은 없다.
