# developer 의 의견 (정기 회의, 2026-10-26 월요일)

진 디자이너 의견을 먼저 읽었다. 아래는 그에 대한 동의/반대와 개발자 관점의 추가 의견이다.

## 지금 서비스에서 내 눈에 가장 걸리는 것
1. **실제 손님이 LIVE 채팅 화면으로 끝까지 주문하는 것을, 개발자인 나조차 실제 네트워크로 한 번도 본 적이 없다.** `OPERATOR_TODO.md` 의 "LAB 시험 주문 1건 부탁드립니다"(10-15, 10-20 두 번 올림)에 지금도 ✅ 표시가 없다. 10-20~10-25 동안 내가 한 모든 확인은 Playwright 정적 렌더링 + 가짜 Firebase 로그인 + 모의 서버 응답이었다(코드 레벨로는 맞다, 그러나 실제 Google 로그인·실제 Apps Script 응답 시간·실제 모바일 키보드는 전혀 포함되지 않았다). R-017로 LIVE 서버가 v2 로 막 교체된 지금, "서버가 37초 걸렸는데 화면이 30초에서 끊던" 10-09 사고가 재발하지 않는다는 보장은 코드를 읽은 것뿐이지 실제로 본 것이 아니다.
2. **"손님 단위 저장소"는 ROADMAP·OPERATOR_TODO 어디에도 결정이 없고, 코드로 확인해 보니 지금은 완전히 없다.** `backend/Code.gs`는 Firebase Auth로 로그인 토큰만 검증하고, 저장은 전부 Google 스프레드시트 한 줄(REQUESTS 시트)뿐이다. Firestore나 Realtime Database는 켜져 있지도, 코드에서 쓰이지도 않는다. "내 브랜드 페이지"·"내 주문 조회"·"이어서 로그인하면 이전 손님임을 알아보기" 전부 지금 구조로는 불가능하고, 이건 설계 변경이 아니라 아예 새 구성요소(DB) 추가라서 가볍게 결정될 일이 아니다.

## 진 디자이너 제안에 대해
1. **LIVE 전체 품질 재점검 — 동의.** 다만 보완: 디자이너가 맡는 "보임" 중심 점검과 별도로, 나는 이번 주 서버 쪽을 본다. 같은 화면이라도 디자이너는 CSS/레이아웃 겹침을, 나는 실제 응답 지연·에러 코드·재시도 흐름을 봐야 한다. 둘이 같은 화면을 다른 각도로 보는 게 중복이 아니라 안전장치라고 본다.
2. **이미지 업로드 방식 결정을 더 미루지 말기 — 강하게 동의.** 개발자로서도 같은 벽에 막혀 있다: Stage 2 의 "로고를 티셔츠에 바로 올려 주문"도 결국 같은 질문(업로드 저장소를 둘지)으로 귀결되고(ROADMAP Stage 2 마지막 줄 "윤 개발자와 의장의 결정이 필요"), 이게 두 번 회의를 건너뛴 채 안 풀리면 Stage 2 설계도 절반만 하게 된다. 기술적으로 덧붙이면: 저장소를 새로 두는 선택(Firebase Storage)은 비용과 별개로 "업로드된 이미지가 PNG 인지, 악성 파일이 아닌지"를 서버가 검증하는 코드가 새로 필요해서 하루 분량이 아니다. 반대로 "미리보기는 당분간 안 한다"는 지금 당장 결론 낼 수 있는 선택이라 나도 이쪽에 투표한다.
3. **COMPONENTS.md 정기 점검 항목 승격 — 동의.** 10-24·10-25 이틀 다 내가 코드를 읽다가 문서와 실제 CSS가 어긋난 걸 "여유 작업"으로 발견했다. 이게 세 번째면 우연이 아니라 패턴이다. 다만 이건 디자이너의 체크리스트보다, 문서와 코드 사이의 어긋남을 신경 쓰는 사람이 느는 게 더 근본적인 해법이라 생각한다 — developer 쪽 작업일에도 같은 점검을 하자고 제안을 더하고 싶다(아래 "이번 주 제안"에 넣음).

## ROADMAP 에 쌓인 기술 안건
- **서버 시험 주문 결과**: 여전히 없다. 10-15, 10-20 두 번 요청했고 아직 ✅가 없다. 이건 AI 팀이 대신할 수 없는 일(Google 로그인은 사람만 할 수 있다)이라 세 번째로 다시 올리는 것 자체가 의미 없을 수도 있지만, 지금은 LIVE 라서 이전보다 무게가 다르다. LAB 시험이 아니라 **LIVE 시험 주문 1건**(지어낸 정보로, 결제는 실제로 안 눌러도 됨)을 요청하는 쪽으로 바꾸고 싶다. 서버가 실제로 막 교체(R-017)됐는데 아무도 실제 네트워크로 끝까지 밟아본 적이 없는 채로 손님들이 쓰고 있다는 게 지금 가장 위험한 지점이다.
- **이탈을 알 방법**: 외부 분석 도구(GA, Mixpanel 등)는 "유료 외부 API 를 새로 붙이지 않는다" 원칙과 충돌하지 않는 선에서도 무료 티어가 있는 것들이 있지만, 그조차 "새로 붙이는 것"이라 제안으로만 남긴다(원칙상 코드로 바로 안 한다). 대신 디자이너 제안대로 **서버 쪽에 최소 로그**를 남기는 안을 검토했다: 지금 `Code.gs`는 성공/실패만 기록하고 "어느 질문 단계까지 입력했다가 포기했는지"는 전혀 남지 않는다. 손님이 중간에 닫으면 서버에 요청 자체가 안 가기 때문에, 서버 로그만으로는 이탈을 못 본다. 화면(`app.js`) 쪽에서 각 단계 진입을 sessionStorage 에 남기는 건 이미 하고 있지만(이어하기 기능), 이걸 서버로 보내는 건 "완료 안 한 손님의 중간 데이터를 서버에 보낸다"는 것이라 개인정보 성격이 달라진다(이름·전화 없이 "step=5에서 멈춤"만 보내는 정도로 최소화해야 한다). 이번 주 안에 설계만 해보고 싶다 — 구현은 다음 주로 넘길 수 있다.
- **손님 단위 저장소**: 위에서 확인한 대로 지금은 전혀 없다. Firebase 프로젝트(`ownstreet-4b808`)는 Auth 만 쓰고 있고, Firestore/Realtime DB 가 켜져 있는지는 Firebase 콘솔 접근 권한이 있는 의장만 확인할 수 있다. 이건 이번 주에 코드로 미리 준비할 수 있는 게 거의 없다 — "켜져 있는지, 켜면 비용이 얼마인지"부터 의장이 답해줘야 다음 설계가 시작된다. 디자이너와 같은 의견: 다다음 회의로 미루지 말고 최소한 "언제 결정할 수 있는지"만이라도 받고 싶다.

## 지금 LIVE 가 실제로 안정적으로 동작하는지 — 가장 위험한 지점
1. **실제 네트워크로 끝까지 테스트 못 해본 것** (위에서 반복했지만 가장 중요해서 다시 적는다). 10-09 사고(서버 37초, 화면 30초에서 끊음)가 보여준 패턴은 "코드는 맞는데 실제 타이밍에서만 드러나는 버그"였다. 그 사고 이후 타임아웃·재시도 로직을 고쳤지만(10/60초 안내, 같은 clientRef 로 재확인), 이것도 실제로 느린 응답에서 본 적은 없다 — 전부 모의 환경이다.
2. **R-017 로 서버가 v2 로 막 바뀐 지 이틀**이고, 10-24·10-25 양일 다 "방금 올라간 기능에서 조용히 깨진 패턴"(`chat.active` 미설정)을 찾아 고쳤다. 비슷한 패턴이 또 있을 가능성을 배제할 수 없다 — 10-25에 점검한 건 `editStep`/`recheckPending`/`settleOldPending` 세 곳이고, 코드 전체를 다 훑은 건 아니다.
3. **느린 응답 시 안내가 실제로 보이는지는 지금도 확인되지 않았다.** 인위적으로 서버를 느리게 만들 방법이 없어서(이건 10-20에도 같이 적은 한계다), 실제 느려짐은 "자연스럽게 느려질 때"에만 발견된다. LIVE 서버가 Apps Script 특성상 가끔 몇십 초씩 걸리는 걸 10-09에 이미 한 번 봤으니, 다시 그런 순간이 오면 그때 10-09 수정이 실제로 작동하는지가 처음 검증된다.

## Stage 2 (네이밍·로고) 착수 시점
**디자이너 의견에 동의한다. 아직은 아니다.** 이유를 개발자 관점에서 더하면: 지금 `app/app.js`(1304줄)는 단계(step) 상태 머신이 전체 흐름을 순서대로 통과한다고 가정하고 짜여 있다. 그 가정이 10-22·10-24·10-25 세 번이나 조용히 깨진(`chat.active`, TDZ, resume) 전례가 있는 코드 위에, Stage 2 의 "브랜드명 후보 → 내가 직접 쓰기 → 로고"라는 새 분기를 바로 얹으면, 새 분기의 버그와 기존 안정화 버그가 뒤섞여 디버깅이 더 어려워진다. 코드를 만지는 입장에서는 "지금 상태 머신이 조용한 한 주"를 먼저 보고 싶다. 네이밍 **로직**(브랜더가 설계하는 단어 조합 규칙) 설계는 화면과 독립적으로 지금 진행해도 전혀 문제없다는 디자이너·브랜더 의견에도 동의한다.

## 이번 주 방향 제안
1. **LIVE 시험 주문 요청을 OPERATOR_TODO 에 다시, 이번엔 "LIVE" 로 명시해 올린다.** 세 번째 요청이라 실행될지는 모르지만, 지금 상태(실제 네트워크 미검증인 채 실제 손님이 쓰는 중)를 반복해서 기록해 두는 것 자체가 의미 있다고 본다.
2. **코드 전체에서 `chat.active` 패턴(그리고 비슷하게 "조건부로만 설정되는 상태 플래그")을 한 번 전수 조사**한다. 10-24·10-25 는 의심되는 세 곳만 봤다. 하루 분량으로 `app.js` 전체의 상태 플래그 설정 지점을 grep 으로 뽑아 각각이 모든 진입 경로에서 설정되는지 확인하는 작업을 제안한다.
3. **이탈 로그 설계(구현 아님)**: 서버에 보내지 않고 sessionStorage 에만 남기는 지금 방식에서, "완료 못 하고 떠난 세션 비율"을 손님 개인정보 없이 알 수 있는 최소한의 방법이 있는지 하루 써서 검토해보고 싶다. 결론이 "지금은 방법이 없다"라도 괜찮다 — 디자이너 말대로 다다음 회의로 또 미루지 않기 위해서다.
4. **디자이너의 LIVE 전체 품질 재점검과 같은 주에, developer 는 서버·에러 경로 쪽 재점검을 병행**한다(진입 경로 전수 조사가 이와 같은 작업이다).

## 다른 팀원 의견에 대해
designer 의 세 제안 모두 동의. 특히 "결론이 미리보기는 당분간 안 한다 라도 좋다"는 입장에 완전히 동의한다 — 결정 없음 상태를 끄는 게 지금 가장 시급하다. 다만 "이탈 파악"에 대해 디자이너가 제안한 "서버에 단계 번호 로그"는, 서버가 요청을 받지 못한 손님(중간 이탈)은 애초에 서버에 닿지 않는다는 점에서 서버만으로는 부족하다는 걸 보완하고 싶었다. 화면(클라이언트)이 각 단계에서 짧은 신호를 보내는 방식이 필요하고, 그 설계부터 이번 주에 해보고 싶다.

## 플랫폼까지 가려면 결국 필요한 것
손님 단위 저장소. 디자이너와 같은 결론이지만 개발자로서 구체적으로 덧붙이면: 지금 구조(세션 하나 + 시트 한 줄)에서는 "같은 손님이 다시 왔다"는 것 자체를 서버가 알 방법이 없다(이메일로 찾을 수는 있지만 그건 매번 전체 시트를 스캔하는 임시방편이고 "내 브랜드"가 쌓일수록 느려진다). Firestore 같은 문서형 DB를 Firebase Auth 의 uid 로 바로 연결하는 게 제일 자연스러운 다음 걸음이라고 보지만, 이건 비용·운영 결정이라 의장 손이 필요하다. 지금 이번 회의에서 "방향"만이라도 받을 수 있으면, Stage 3 설계를 미리 그 방향에 맞춰 짤 수 있다.
