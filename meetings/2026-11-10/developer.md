# developer 의 의견 (정기 회의, 2026-11-10 화요일 — 새 회의 요일 첫 회의)

진 디자이너 의견을 먼저 읽었다. 오늘은 평소보다 안건이 크다 — 회의 요일 변경(R-029)과 피벗(R-028)이 겹쳤다. 코드는 건드리지 않고, 코드를 읽고 확인한 사실만 가지고 의견을 낸다.

## 지금 서비스에서 내 눈에 가장 걸리는 것
1. **`STEPS` 배열은 "주문"을 완결 단위로 가정하고 있는데, 피벗의 완결 단위는 "자호(이름+뜻)"다.** 코드로 직접 확인했다: `app/app.js` 27행 `const STEPS = ['url', 'story', 'size', 'name', 'phone', 'address', 'memo']`. 지금 이 배열의 끝은 배송 메모다 — 완결 단위가 "결제 가능한 주문 한 건"이라는 뜻이다. 분석 문서(`docs/strategy/00_시장성_분석.md`)의 결론대로 완결 단위가 "호 하나 + 뜻 한 줄"이라면, 이 배열의 **맨 앞**에 완전히 새 질문이 필요하고, 그 질문이 끝나는 자리에서 이미 "완결"이 일어나야 한다 — 지금처럼 사이즈·전화번호·주소까지 다 가야 완결이 아니다. 디자이너가 어제 쓴 말("질문 하나만 끼워 넣는 식으로는 안 된다")에 전적으로 동의한다. 내 쪽에서 코드로 덧붙이면, 이건 질문 문구 교체가 아니라 **"완결이 어디서 일어나는가"를 다시 정의하는 상태 머신 변경**이다. 지금 당장 할 일은 아니라고 본다 — 이번 주 작업일이 이틀뿐이고(R-029), 1기 모임은 사람 손으로 진행한다(R-028②).
2. **`backend/Code.gs` 의 열 추가 패턴은 피벗에도 그대로 쓸 수 있다는 걸 오늘 코드로 재확인했다.** `HEADERS`(48행) 바로 위 주석에 "열 순서는 바꾸지 않습니다. 새 열은 항상 맨 뒤에 덧붙입니다"라고 이미 적혀 있고, v0→v2 때(접수번호~상태 7칸 → 사이즈~동의시각 13칸) 실제로 이 방식으로 확장한 전례가 있다. "자호(이름+뜻)" 를 나중에 서버에 저장하게 되더라도, 기존 `REQUESTS` 시트·접수번호 발급 로직을 건드리지 않고 맨 뒤에 칸 두 개(호, 뜻)만 더하는 식으로 갈 수 있다 — 구조적으로 어렵지 않다. 다만 **지금 결정할 일은 아니다**, 1기 모임은 사람이 진행하고 서버 저장이 필요한 단계가 아니기 때문이다(R-028②, 분석 문서 결론 "지금은 사람이 함께하는 체험부터").

## 남길 것 / 바꿀 것 / 멈출 것 (개발자 영역)

**남길 것**
- `backend/Code.gs` 의 접수번호 발급 로직(저장 확인 뒤에만 OS-번호 발급, clientRef 중복 방지, 헌장의 "가짜 성공 금지" 원칙을 구현한 부분)은 피벗과 무관하게 그대로 둔다. R-028③이 "LIVE 주문 서비스는 그대로 둔다"고 명시했고, 지금 실제 고객이 쓰고 있다. 자호 짓기가 나중에 주문과 합쳐지더라도 이 안전장치는 그대로 재사용된다.
- `app/app.js` 의 채팅 상태 머신 틀(디자이너가 말한 "질문-답-카드" 패턴, `COMPONENTS.md` 의 `.card.wide`·`.bubble`·입력 종류 네 가지)도 틀 자체는 재사용 가능. 질문의 **내용**이 바뀌는 것과 질문을 **주고받는 틀**이 바뀌는 것은 다른 일이고, 틀은 바꿀 이유가 없다.
- 11-08 에 올린 funnel ping(이탈 집계, `docs/funnel-drop-off-design.md`)은 피벗 이후에도 유효하다 — 이탈을 보는 지점이 "주문 단계"든 "자호 짓기 단계"든 똑같이 필요한 질문("손님이 어디서 멈추는가")이기 때문이다. 다만 아직 LAB·LIVE 양쪽 서버에 반영되지 않아 집계가 하나도 쌓이지 않은 상태다(OPERATOR_TODO 11-08 요청, 처리 표시 없음 — 아래에서 다시 확인).

**바꿀 것**
- 지금은 바꿀 게 없다고 본다. 코드를 미리 "피벗에 맞춰" 고쳐두는 건 분석 문서가 짚은 위험 신호 4번("덧붙이기 — 지금 서비스 위에 더하면 일이 두 배가 된다")에 정확히 걸린다. 플랫폼 계획이 의장 확정 전까지는, STEPS 배열이나 Code.gs 저장 칸을 먼저 손대지 않는 쪽이 맞다.

**멈출 것**
- **10-30 이탈 로그 "구현" 쪽 확장은 지금 더 진행하지 않는다.** ping 자체(집계 5지점)는 이미 다 짰고 서버 반영을 기다리는 상태라 거기서 멈추는 게 맞다 — 더 세분화된 단계별 로그를 피벗 전의 STEPS 기준으로 추가 설계하는 건 피벗으로 STEPS 자체가 바뀔 걸 감안하면 헛수고가 될 수 있다.
- `docs/naming-rules.md` 쪽 "코드화" 작업(신 브랜더의 네이밍 로직을 서버/화면에 미리 얹는 작업)도 지금은 멈춘다. 디자이너가 어제 같은 취지로 "브랜드 후보 카드 틀"을 보류했다 — 이유가 같다. 질문지·네이밍 규칙은 **이번 주엔 사람 손으로 1기 모임용 워크북**에 들어가는 거고, 그게 화면 코드로 들어오는 건 플랫폼 단계(2단계) 얘기다.

## 1기 모임(11-19) 준비물에 대해
작업일이 목(11-12)·일(11-15) 이틀뿐이고, 준비물(질문지·워크북)은 사람이 진행할 인쇄물이라 코드가 할 일이 적다는 걸 인정한다. 대신 이 이틀에 개발자가 할 수 있는 건 둘이라고 본다.
1. **LIVE 서버를 그대로 안정적으로 지키는 것.** R-028③이 "LIVE 주문 서비스는 그대로 둔다"고 했으니, 이번 주는 LIVE 를 더 건드리지 않는 게 오히려 할 일이다. 다만 아래 "밀린 안건"에 적은 funnel ping 반영은 예외로 요청해 둔다 — 이미 짜 둔 걸 그냥 묵혀 두는 것도 낭비다.
2. **디자이너가 남긴 질문에 답한다.** Anton 폰트의 인쇄 라이선스는 내 영역이 아니지만(의장 요청 없이는 유료 라이선스 확인도 내 손으로 결제·계약을 알아볼 수 없다), 디자이너가 "모르면 직접 찾아보겠다"고 먼저 말했으니 금요일(다음 작업일, 11-14 발행 기준으로는 디자이너의 다음 작업일)에 맡긴다. 개발자가 보탤 수 있는 건 실무적인 것 하나 — Anton 은 Google Fonts 배포 폰트라 OFL(오픈 폰트 라이선스) 적용이고, OFL 은 인쇄물 포함 모든 매체에 무료 사용이 허용되는 경우가 보통이다(Google Fonts 에 올라온 폰트는 대부분 OFL). 다만 이건 내가 라이선스 전문(원본 OFL.txt) 을 직접 열어 확인한 게 아니라 **일반적으로 알려진 사실**을 전하는 것이라, 디자이너가 직접 한 번 더 확인해 주면 좋겠다.

## 밀린 안건 (OPERATOR_TODO.md 확인)
- **LIVE 시험 주문(10-26, 세 번째 요청, 내가 낸 제안)**: 아직 ✅ 표시가 없다. 디자이너와 같은 결론을 낸다 — 피벗으로 우선순위가 낮아졌다고 본다. 지금 더 급한 건 1기 모임 준비이고, LIVE 서버 자체는 R-017 이후 큰 변경이 없었다. 다시 올리기보다 **당분간 보류로 접는다.** 다만 이건 "문제없다"는 뜻이 아니라 "아직도 실제 네트워크로 끝까지 검증된 적이 없다"는 사실은 그대로 남아 있다는 걸 기록만 해 둔다.
- **손님 단위 저장소(Firestore 여부)**: 세 번째(10-11, 10-26) 요청에도 답이 없다. 분석 문서 결론("셀프 플랫폼은 나중")에 비춰 이것도 우선순위가 낮아졌다고 본다 — 내 브랜드 페이지·주문 조회 같은 저장소가 필요한 기능 자체가 지금 로드맵에서 뒤로 밀린 기능이다. 네 번째로 다시 올리지 않고 **보류로 접는다.** 플랫폼 2단계가 의장 확정으로 다시 열릴 때 꺼내겠다.
- **funnel ping LAB·LIVE 반영(11-08 요청)**: `OPERATOR_TODO.md` 맨 끝 줄을 확인했다 — 아직 처리 표시가 없다. 이건 위 둘과 달리 **보류로 접지 않는다.** 이유: 이미 다 짜고 모의 테스트(191개)까지 통과한 상태라, 반영만 하면 되는 "거의 끝난 일"이고, 개인정보를 전혀 받지 않는 완전히 분리된 시트(`FUNNEL`)라 피벗 방향과도 충돌하지 않는다. 다만 이번 주 우선순위(1기 모임)보다 뒤에 와도 괜찮다고 생각한다 — 급한 일은 아니다.

## 다른 팀원 의견에 대해
designer 의견에 전반적으로 동의한다.
- "디자인 시스템 자체는 남긴다"에 동의. 톤을 바꿀 이유가 없다는 판단에 개발자 쪽 근거를 하나 더한다: 화면 틀(채팅 질문-답-카드)과 디자인 시스템(색·폰트·그림자)은 코드에서도 서로 독립된 레이어다(`styles.css` 의 토큰과 `app.js` 의 상태 머신은 분리돼 있다). 톤을 지키면서 질문 내용만 바꾸는 게 기술적으로도 자연스럽다.
- "STEPS 순서·질문 내용이 바뀌어야 한다"에 동의. 다만 디자이너 의견엔 "지금 당장 끼워 넣는 식으로는 안 된다"까지만 있고 "그래서 지금 당장 다시 짜야 한다"는 결론은 없다 — 나도 지금 당장 다시 짜는 쪽에는 반대다. 플랫폼 계획이 의장 확정 전이라 상태 머신을 먼저 바꾸면 분석 문서 위험 신호 4번("덧붙이기")에 걸릴 수 있다.
- "브랜드 후보 카드 틀 보류"에 동의 — 같은 이유로 나도 네이밍 로직의 코드화를 멈추는 쪽에 섰다(위 "멈출 것" 참고). 둘이 독립적으로 같은 결론에 닿았다는 게 이 판단이 맞다는 신호라고 본다.
- "손님 이미지 업로드 방식 보류"에도 동의. 다만 이유를 하나 덧붙이면, 이건 디자이너 말대로 "피벗으로 전제가 바뀐 것"이기도 하지만 **원래도 세 번 미뤄진 안건**이다 — 내가 10-26 에 같은 걸 "Stage 2 도 이 결정에 막혀 있다"고 적었던 게, 이제는 Stage 2 자체가 바뀌어 저절로 풀렸다. 디자이너가 "플랫폼 단계에 다시 들어갈 때 꺼내겠다"고 한 데 동의한다.
- Anton 폰트 질문에는 위에서 답을 남겼다 — 일반적으로 OFL 라이선스라 인쇄물 포함 무료 사용이 통상적이지만, 내가 원문 라이선스 파일을 직접 열어 확인한 건 아니므로 디자이너가 한 번 더 확인해 주면 확실하다.

## 의장의 선언문에 비추어, 내 분야에서 가장 먼저 다가갈 수 있는 것
선언문의 핵심은 "AI 는 도구, 마지막 선택은 사용자가 한다"다. 개발자로서 지금 가장 먼저 다가갈 수 있는 건 새 기능이 아니라 **지금 있는 안전장치를 건드리지 않는 것**이다 — 접수번호는 서버가 저장을 확인한 뒤에만 발급하고, 가짜 성공을 만들지 않는 지금의 원칙이 "자기가 직접 끝낸 것만 인정한다"는 선언문의 정신과 이미 같은 방향이다. 자호 짓기가 들어와도 이 원칙(서버 확인 전 가짜 완결 금지)은 똑같이 적용돼야 한다고 생각한다.

## 플랫폼까지 가려면 결국 필요한 것
디자이너와 같은 결론 — STEPS 를 "주문 전용"에서 "자기 이름 짓기 전용"으로 다시 짜는 화면 재설계. 거기에 개발자 관점을 하나 더하면, 그 재설계가 일어날 때 지금 있는 안전장치(저장 확인 후 발급, clientRef 중복 방지, 재시도 로직)를 새 완결 단위("호 하나 완성")에 맞춰 옮기는 작업도 같이 와야 한다 — 이건 화면만 다시 그린다고 되는 일이 아니라 Code.gs 의 "무엇을 저장 확인의 기준으로 볼 것인가"도 같이 바뀌는 일이다. 지금은 아니고, 플랫폼 계획이 확정된 뒤의 일이다.

## 다음 사람(brand-feature-developer)에게
네이밍 규칙(`docs/naming-rules.md`)의 코드화를 이번 주는 같이 멈추자고 제안했다. 대신 이번 주에 그 규칙을 **워크북 질문 문구**로 사람이 쓸 수 있게 다듬는 쪽에 힘을 쏟아주면 좋겠다 — 디자이너가 "신 브랜더가 먼저 질문 문구 초안을 내고 디자이너가 레이아웃에 앉히는 순서"를 제안했는데, 나도 같은 순서가 맞다고 본다. 그리고 궁금한 것 하나 — 분석 문서가 말한 "손님 단어를 이름에 남기는 로직"이 "호"(이름 하나 + 뜻 한 줄)라는 새 완결 단위에도 그대로 들어맞는지, 아니면 그 로직도 피벗에 맞춰 손볼 부분이 있는지 궁금하다.
