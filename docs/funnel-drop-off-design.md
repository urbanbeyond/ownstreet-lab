# 이탈 로그 설계 (검토, 2026-10-30)

ROADMAP Stage 1 "단계별 이탈을 알 방법"(10-11부터 미해결, 10-26 회의에서 다시 확인)에 대한
검토 문서. **이 문서는 설계일 뿐 구현이 아니다.** `app/app.js`, `backend/Code.gs` 는 오늘 바꾸지 않았다.

## 0. 먼저 분명히 할 것 — 질문을 다시 쓴다

"완료하지 못한 세션 비율을 알고 싶다"는 목표를 그대로 풀면, 보통은 "모든 세션에 익명 ID를 매겨
각 단계 진입/이탈을 서버나 분석 도구에 보낸다"가 답이다. 하지만 그 답은 우리 제약 두 개와
정면으로 부딪힌다.

- **유료 외부 분석 서비스를 새로 붙이지 않는다** (GA, Mixpanel 등 — 10-26 회의에서 이미 기각).
- **개인정보를 코드·로그 어디에도 넣지 않는다.** "세션 추적"은 익명이라도 쿠키/디바이스 ID 류의
  식별자를 새로 만들어 쌓는 행위이고, 이게 사실상 개인정보 수집 범위를 넓히는 일이라서 신중해야
  한다.

그래서 이 검토의 결론은 **"이탈률을 정확히 재는 새 수집 체계를 만들자"가 아니라, "지금 있는
세 가지 신호로 어디까지 볼 수 있고 어디부터는 못 보는지를 명확히 긋자"** 다. 아래는 그 경계선이다.

## 1. 사용자가 밟는 단계와 지금 가진 신호

실제 흐름(`app/app.js` `STEPS` + 로그인 + 확인 + 접수):

```
(0) 진입/주문 시작 버튼
 → url → story(건너뛰기 가능) → size
 → [로그인] (name 질문 직전, askLogin())
 → name → phone → address → memo(건너뛰기 가능)
 → confirm(주문 확인 카드, 동의 체크박스)
 → placeOrder() → submitOrder() → 서버 응답
 → (완료) showComplete() 접수번호 발급
```

지금 있는 세 가지 수단과 각각이 "보는 범위":

| 수단 | 무엇을 아는가 | 누가 볼 수 있는가 | 언제 사라지는가 |
|---|---|---|---|
| **서버 시트 줄**(`backend/Code.gs` `REQUESTS`) | **완료된** 요청만. `processRequest_()` 가 호출되고 저장+재확인까지 끝난 경우에만 한 줄이 생긴다. | 의장(스프레드시트 소유자) | 지우지 않으면 영구 |
| **`sessionStorage` draft**(`DRAFT_KEY = 'ownstreet.order.v1'`) | 그 손님의 **그 탭**이 지금까지 입력한 답(`chat.data`). 서버로 전송되지 않는다. | 그 손님의 그 브라우저 탭뿐. 팀은 절대 못 봄(서버에 없음) | 탭을 닫으면 사라짐. 로그아웃 시 `clearSessionData()` 가 지움 |
| **브라우저 콘솔**(`console.info/warn/error`) | 그 손님의 그 브라우저가 지금 켜져 있는 개발자 도구에 찍히는 로그(접수 시도 횟수·걸린 시간·결과 코드 — `attemptRequest()` 706행) | 그 손님 자신뿐(개발자 도구를 열어야 보임). 팀은 원격으로 수집할 길이 없음 | 탭을 닫으면 사라짐 |

**핵심 결론: 이 세 가지 중 어느 것도 "팀이 나중에 모아서 볼 수 있는, 중간에 그만둔 세션의 집계"를
만들지 못한다.** 서버 시트는 완료된 것만 알고, sessionStorage와 콘솔은 그 손님의 기기 밖으로
나가지 않는다. 이게 오늘 검토에서 가장 먼저 확인한, 그리고 가장 중요한 사실이다.

## 2. 그래도 "완료 못한 세션 비율"에 조금이라도 다가갈 수 있는 지점이 있는가

세 가지 신호 중 유일하게 "서버가 알고 있는" 것은 **시트에 저장된 완료 건수**다. 완료 건수 자체는
이미 존재한다(접수번호 OS-0001, OS-0002 …의 개수). 문제는 "분모"(시작한 세션 수)를 전혀 모른다는
것이다. 분모 없이는 "비율"을 말할 수 없다.

검토한 네 가지 방법과 왜 채택하지 않는지:

### (A) 서버에 "세션 시작" 신호를 추가로 보낸다
로그인 직후나 `beginOrder()` 시점에 서버로 핑(ping) 한 번을 보내 "시작됨" 카운트를 늘린다.
- 분모를 만들 수 있다는 점에서 유일하게 "비율"을 말할 수 있는 방법이다.
- 하지만 **서버 코드 변경(새 액션 추가) + 배포가 필요**하다. PM 지시대로 오늘은 코드를 바꾸지
  않으므로 이 자리에서는 구현하지 않는다. (다음 날 작업으로 넘길 수 있는 후보로 2절에 남긴다.)
- 개인정보 문제는 없다 — uid·이메일 없이 "시작 1건" 신호만 보내면 된다(로그인 전에도 보낼 수
  있는 신호라 uid가 필요 없음).
- 단, 새 시트/새 열이 생기므로 **의장 배포가 필요**하고, "시작"과 "완료"를 같은 사람의 같은
  시도로 잇지 않으면(= 익명 집계로만 쓰면) 개인정보 문제 없이 분모/분자 비율만 얻을 수 있다.

### (B) 서버 시트의 "중간에 멈춘 흔적"을 읽는다
Code.gs 는 저장이 재확인된 경우에만 줄을 쓴다(`processRequest_()` 222~231행, "다시 읽어 확인"
실패 시 `SERVER_ERROR`를 던지고 줄은 시트에 남을 수 있다 — API.md 7절 "읽기 확인에 실패했지만
줄은 시트에 남은 경우"). 이론적으로 이 "접수번호는 없지만 줄은 있는" 사례를 세면 "서버까지는
도달했지만 확인에 실패한 세션"의 힌트를 얻을 수 있다.
- 하지만 이건 **고객 데이터가 있는 시트를 열어봐야 하는 방법**이라 AI 팀 규칙(스프레드시트 접근
  금지)과 충돌한다. 의장만 볼 수 있고, AI 팀은 코드로 자동화할 수 없다.
- 그리고 이 경로는 로그인조차 못 한 사람, URL/이름/전화 단계에서 그만둔 사람은 전혀 잡지
  못한다(서버에 요청 자체가 안 갔으므로). "일부 이탈"만 보이는 매우 좁은 창이다.

### (C) sessionStorage draft를 "익명 통계"로 바꿔 서버에 보낸다
탭을 닫기 전에(`beforeunload`) 지금까지 어느 단계까지 왔는지만(개인정보 제외, 예: `"step":"phone"`)
보내는 방법.
- `beforeunload`/`visibilitychange` 이벤트는 모바일 브라우저(특히 iOS Safari, 인앱 브라우저)에서
  신뢰도가 낮다 — 발화 자체가 안 되거나, fetch가 끝나기 전에 탭이 죽는 경우가 흔하다. "측정은
  됐는데 실제보다 적게 잡힌다"는 왜곡이 구조적으로 생긴다.
- 이것도 **서버에 새 수신 지점이 필요**해 오늘 범위(코드 변경 없음) 밖이다.
- 개인정보 관점에선 비교적 안전하게 설계할 수 있다(단계 이름만, uid 없음, IP는 Apps Script
  액세스 로그에만 남고 코드가 직접 다루지 않음)는 점은 (A)보다도 낫다. 다만 신뢰도 문제로 (A)
  보다 부정확하다.

### (D) 외부 분석 서비스(GA, Mixpanel, PostHog 등)
가장 쉽고 정확하지만 **유료 외부 API를 새로 붙이지 않는다는 원칙과 바로 충돌**한다(10-26 회의
에서 이미 기각됨, `ROADMAP.md` "채택하지 않은 제안" 참고). 무료 티어가 있어도 "새로 붙이는
외부 서비스"라는 점은 같다. **오늘도 제안으로만 남기고 코드로 만들지 않는다.**

## 3. 오늘의 결론

1. **지금 있는 세 가지 수단(서버 시트, sessionStorage, 콘솔)만으로는 "단계별 이탈 비율"을
   전혀 집계할 수 없다.** 셀 수 있는 것은 "완료된 접수 수"뿐이고, 분모(시작한 세션 수)가 없다.
   이건 설계를 더 다듬어서 풀 수 있는 문제가 아니라, 구조적으로 막혀 있는 것이다 — 서버가
   모르는 일은 서버가 셀 수 없다.
2. "비율"을 알고 싶다면 **서버에 최소 하나의 새 신호(세션 시작 핑, 방법 A)가 필요**하고, 이는
   `backend/Code.gs` 수정 + 의장 배포가 있어야 가능하다. **오늘은 이 코드를 만들지 않는다**
   (PM 지시: 구현 아님, 설계만).
3. 외부 분석 서비스(방법 D)는 원칙상 계속 배제한다.
4. sessionStorage draft를 읽어 "중도 이탈 신호"를 서버로 보내는 방법(C)은 모바일 신뢰도가
   낮아 (A)보다 우선순위가 낮다고 본다.

## 4. 구현한다면 — 다음에 쓸 최소 설계 초안 (참고용, 오늘 코드화 아님)

실제로 다음 날 작업으로 이어진다면 아래가 "가장 작은 범위"일 것 같다.

- **서버**: `Code.gs` 에 `action: 'ping'` 같은 새 액션 하나. 받으면 `FUNNEL` 이라는 별도 시트(또는
  `REQUESTS` 와 다른 전용 시트)에 `{ date, step }` 두 칸만 한 줄 추가. 이메일·이름·uid·idToken은
  받지도 저장하지도 않는다 — 로그인 여부와 무관하게 호출 가능해야 로그인 전 이탈도 잡을 수
  있다.
- **클라이언트**: `beginOrder()`, `askLogin()` 도달, `name` 단계 진입(=로그인 완료), `showConfirm()`,
  `placeOrder()` 시작 다섯 지점 정도에서 "단계 이름"만 담아 1회성 `fetch`(응답을 기다리지 않고
  실패해도 무시, `keepalive: true` 옵션으로 탭 종료 중에도 전송 시도)를 보낸다. 네트워크 실패 시
  재시도하지 않는다(이 신호는 통계용이라 완벽할 필요가 없고, 재시도 로직을 넣는 순간 본래
  목적(가벼움)을 잃는다).
- **분석**: 날짜별로 각 단계 이름이 몇 번 찍혔는지만 세면, "100명이 시작 → 80명이 로그인 →
  60명이 확인 화면 → 55명이 완료"같은 **깔때기(funnel) 집계**가 나온다. 개인별 추적이 아니라
  **그 날의 숫자 집계**이므로 개인정보 문제가 거의 없다(IP는 Apps Script 실행 환경이 자동으로
  보는 것 이상으로 코드가 다루지 않음).
- **한계를 미리 인정**: 이 방법도 "같은 사람이 재시도/새로고침해서 같은 단계가 중복 기록"되는
  것까지는 완벽히 막지 못한다(세션 ID 없이 가는 쪽을 택했으므로). 정확한 세션 단위 추적이
  아니라 "대략의 깔때기 모양"을 보는 용도로만 써야 한다. 더 정확히 하려면 세션 식별자가
  필요해지는데, 그건 다시 "익명이라도 식별자를 쌓는 것"의 경계를 넘는 문제라 별도로 다시
  의논해야 한다.

## 5. 왜 오늘은 여기서 멈추는가

PM 목표가 명확히 "구현 아님, 설계·문서"였고, 검토 결과도 "지금 수단으로는 집계가 안 된다 →
집계하려면 서버 코드가 필요하다 → 서버 코드는 오늘 다루지 않는다"로 자연스럽게 이어진다.
억지로 "측정 가능한 범위"를 부풀리기보다, **안 되는 것을 안 된다고 쓰는 것**이 이 문서의
목적에 맞는다고 판단했다.
