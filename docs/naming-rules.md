뒤, 그리고 실제 손님의 story 답변이 쌓인 뒤 이 규칙을 다시 맞춰보고 코드화한다.

## 0. 전제와 한계 — 먼저 밝혀둔다

- **실제 손님의 story 답변은 아직 하나도 없다.** `docs/chat-script.md`(10-17)를 쓸 때도 같은
  문제가 있었고, 10-26 회의에서도 신 브랜더 본인이 이 점을 가장 먼저 짚었다. OPERATOR_TODO 에
  관찰 가능 여부를 질의했으나 오늘까지 답이 없다(PM 결정문에도 "보류"로 명시).
- 그래서 이번 문서는 **본인이 직접 다양한 길이·어투의 샘플 문장 20개를 만들어 규칙을 시험**하는
  방식으로 대신한다(10-26 회의에서 본인이 제안한 대안). 아래 "5. 샘플 문장으로 시험"이 그 결과다.
  **이 샘플은 추측이다.** 실제 손님 답변이 쌓이면 이 문서의 사전·규칙은 다시 맞춰야 한다 — 특히
  "한국어 조사·종결어미를 얼마나 거칠게 잘라내도 되는지"는 실제 문장을 봐야 확신할 수 있다.
- 이 기능은 **AI 가 대신 정해주고 끝나는 게 아니다.** 선언문 기준대로, 후보는 항상 "다시 뽑기"와
  "내가 직접 쓰기"를 함께 둔다(아래 6번). 규칙·사전이 만드는 건 **출발점**이고, 마지막 선택은
  손님이 한다.

## 1. 전체 흐름

```
입력: story (손님이 쓴 한 줄, 1~200자. 비어 있을 수 있음 — 건너뛰기 가능 질문)
  ↓ 1단계: 키워드 추출 (조사·종결어미 제거, 핵심 단어 1~3개 뽑기)
  ↓ 2단계: 단어 치환 (일상어 → 브랜드스러운 단어, 사전 매핑)
  ↓ 3단계: 세 가지 축으로 각각 조합 (직설적 / 은유적 / 영어조합)
  ↓ 4단계: 접두어·접미어 사전과 결합해 각 축마다 1~2개, 총 3개 이상 후보 생성
출력: 브랜드명 후보 목록(서로 다른 방향 3개 이상) + 왜 그 이름인지 한 줄 설명
      + "내가 직접 쓰기" 입력창 + "다시 뽑기" 버튼 (항상 함께)
```

story 가 비어 있으면(건너뛴 손님) 네이밍 단계 자체를 건너뛰거나, 키워드 없이 접두어/접미어
사전만으로 "일반 후보"를 보여주는 두 가지 길이 있다 — 이건 화면 설계(디자이너 몫)와 맞물려
있어 이 문서에서는 선택지로만 남긴다.

## 2. 1단계 — story 에서 키워드 뽑기

### 2-1. 전처리
- 양끝 공백 제거, 마침표·물결·이모지 제거(이모지는 브랜드명에 쓰지 않는다 — 인쇄물에 올라갈
  이름이라 특수문자 없는 쪽이 안전).
- 문장을 공백 기준으로 토큰 분리.

### 2-2. 조사·종결어미 제거 (규칙 기반, 형태소 분석기 없이)
외부 라이브러리 없이 브라우저 안에서 돌아가야 하므로, **흔한 조사·어미를 꼬리에서부터 긴 것부터
매칭해 잘라내는 방식**을 쓴다(정교한 형태소 분석은 아니지만 짧은 한 줄 문장에는 충분히 작동).

```js
// 긴 꼬리부터 먼저 시도 (짧은 조사가 긴 조사 안에 포함되는 경우가 있어 순서가 중요하다)
const TAIL_PATTERNS = [
  '이라는', '이었던', '하는', '했던', '한다', '했다', '이다', '였다',
  '에게', '에서', '으로', '로써', '처럼', '같이', '만큼',
  '이고', '이며', '이지만', '하고', '하지만',
  '은', '는', '이', '가', '을', '를', '에', '의', '와', '과', '도', '만',
];
```
- 토큰 끝에서 패턴을 매칭되는 즉시 잘라낸다. 두 글자 이하 토큰은 자르지 않는다(과하게 잘려
  의미 없는 글자만 남는 것 방지. 예: "색"은 그대로 둔다).
- 동사/형용사형 토큰("만들었어요", "좋아해요" 등)은 명사가 아니라서 브랜드명 재료로 쓰기
  어렵다 — 이런 토큰은 **키워드 후보에서 제외**하고, 명사형 토큰만 남긴다. 판별은 완벽할 수
  없으니 "흔한 동사 종결 패턴 목록"(`~어요`, `~았다`, `~한다` 등으로 끝나는 토큰)으로 거른다.

### 2-3. 핵심 단어 선정
- 남은 토큰 중 2글자 이상인 것을 핵심 단어 후보로 삼는다.
- 우선순위: ① 색/계절/동물/자연물처럼 **구체적 이미지 단어**(아래 사전에 있는 단어) > ② 감정/
  가치 단어("자유", "용기" 등) > ③ 그 외 명사.
- 핵심 단어 1~3개를 남긴다. 토큰이 하나뿐이면 그거 하나만 쓴다.
- 영어 단어가 섞여 있으면(예: "나의 street") 그대로 핵심 단어 후보에 포함한다 — 영어조합 축에서
  바로 쓸 수 있다.

## 3. 2단계 — 손님 단어 치환 사전

손님이 쓴 일상어를 그대로 쓰면 밋밋하거나, 반대로 브랜드명으로 쓰기엔 너무 평범한 경우가 많다.
**치환은 "다른 단어로 바꿔치기"가 아니라 "같은 단어의 더 선명한 버전을 보여주는 것"**이어야
한다 — 손님이 쓴 단어가 사라지면 "내 이야기가 담긴다"는 선언문 기준을 어기게 된다. 그래서 치환
결과에는 항상 **원래 단어도 함께 보여준다** (예: 후보 설명에 "너의 '색'에서").

**사전은 완성본이 아니다.** 실제 손님 답변이 쌓이면 가장 자주 나오는 단어 중심으로 사전을

### 3-3. 치환 원칙
- 치환은 **선택사항**이다 — 원래 단어 그대로 쓰는 후보도 항상 하나는 포함한다(직설적 축이
  이 역할을 한다. 아래 4번).
- 사전에 없는 단어는 치환하지 않고 그대로 쓴다. 억지로 끼워 맞추지 않는다 — 차라리 접두어/
  접미어만으로 꾸민다.
- 치환 후보는 사전마다 2~3개로 제한한다. 너무 많으면 "어느 걸 골라야 할지 모르는" 선택 피로가
  생긴다.

## 4. 3단계 — 방향을 가르는 세 가지 축

같은 재료(키워드)로 **서로 다른 세 방향**을 만든다. "서로 다른 방향 3개 이상"(PM 역할 설명)의
실체가 이 축이다. 세 축은 "같은 단어를 얼마나 가깝게/멀게 다루는가"의 차이다.

### 축 1 — 직설적 (Literal)
손님이 쓴 단어를 **거의 그대로**, 치환 없이 쓴다. 접두어/접미어로 브랜드 느낌만 더한다.
가장 "내 이야기가 담겼다"는 확신이 드는 축 — 가장 안전하고, 가장 보수적이다.

- 규칙: `[핵심 단어]` + `[접미어 사전 중 하나]` 또는 `[접두어 사전 중 하나]` + `[핵심 단어]`
- 예시 (핵심 단어: "색"): `색 스트릿`, `마이 색`, `색 하우스`
- 예시 (핵심 단어: "새벽"): `새벽 하나`, `디어 새벽`, `새벽 공방`

### 축 2 — 은유적 (Metaphor)
핵심 단어를 **치환 사전(3-1, 3-2)**으로 바꾸거나 확장해서, 손님이 쓴 단어가 바로 보이지는
않지만 뜻은 이어지게 만든다. 손님 단어는 후보 설명("너의 '색'에서 번져 나온 이름")에서
밝혀준다 — 숨기는 게 아니라 "한 걸음 번역"하는 것.

- 규칙: `[치환 단어]` + `[접미어]` 또는 `[접두어]` + `[치환 단어]`, 혹은 두 치환 단어를 조합
- 예시 (핵심 단어: "색" → 치환 "빛깔"): `빛깔 하나`, `첫 빛깔`
- 예시 (핵심 단어: "자유" → 치환 "날개"): `날갯짓`, `무명의 날개`
- 예시 (핵심 단어: "새벽" → 치환 "여명"): `여명 공방`, `여명과 걸음` (두 치환어 조합: "여명" +
  "걸음"의 치환어 "보폭"을 섞지 않고, 2단계에서 뽑은 두 번째 키워드가 있으면 그것과 조합)

### 축 3 — 영어조합 (English Mix)
핵심 단어(또는 치환 단어)의 **영어 버전**을 접두어/접미어 사전의 영어 단어와 조합한다. 스트릿
웨어 브랜드 이름에 흔한 패턴(짧은 영단어 2개 붙이기, 대문자, `.`이나 `_` 같은 기호 하나 섞기)을
따른다. 다만 기존 실존 브랜드명을 베끼지 않도록 **고유명사가 아닌 일반 단어 조합**만 쓴다.

- 규칙: `[영어 치환 단어]` + `[영어 접미어]` 또는 `[영어 접두어]` + `[영어 치환 단어]`
- 예시 (핵심 단어: "색" → "HUE"): `HUE WORKS`, `OWN HUE`, `HUE.CO`
- 예시 (핵심 단어: "자유" → "FREE"): `FREE LINE`, `FREE STUDIO`, `DAY ONE FREE`
- 예시 (핵심 단어: "새벽" → "DAWN"): `DAWN WORKS`, `DAWN.CO`, `MY DAWN`

## 5. 접두어/접미어 사전

세 축 모두에서 재사용하는 "브랜드 느낌을 더하는 조각"이다. **스트릿웨어 분위기 + 선언문의
"자기만의 것" 정신**을 기준으로 골랐다. 실존 브랜드 접미어(예: 특정 유명 브랜드의 시그니처
접미어)를 베끼지 않도록, 흔하게 쓰이는 범용 단어 중심으로만 담았다.

### 5-1. 한국어 접두어 (핵심 단어 앞에 붙임)
| 접두어 | 느낌 |
|---|---|
| 마이 | 소유·개인화 ("마이 색") |
| 디어 | 다정하게 부르는 말 ("디어 새벽") |
| 무명의 | 익명·겸손 ("무명의 날개") |
| 첫 | 시작·처음 ("첫 빛깔") |
| 홀로 | 혼자·독립 ("홀로 걸음") |

### 5-2. 한국어 접미어 (핵심 단어 뒤에 붙임)
| 접미어 | 느낌 |
|---|---|
| 하나 | 단수·고유함 ("색 하나") |
| 공방 | 만드는 곳, 수공업 느낌 ("새벽 공방") |
| 상회 | 가게·상점의 옛말, 스트릿 브랜드에 흔한 레트로 느낌 ("길 상회") |
| 과 걸음 | 동행·여정 ("바람과 걸음") |
| 하우스 | 모임·거점 ("색 하우스") |

### 5-3. 영어 접두어
| 접두어 | 느낌 |
|---|---|
| OWN | 선언문·서비스명과 직결 ("OWN HUE") |
| DAY ONE | 처음·시작 ("DAY ONE FREE") |
| MY | 소유·개인화 ("MY DAWN") |
| NO NAME | 익명·반권위 ("NO NAME WAVE") |

### 5-4. 영어 접미어
| 접미어 | 느낌 |
|---|---|
| WORKS | 제작·공방 느낌, 스트릿웨어에 흔함 |
| STUDIO | 작업실, 브랜드 느낌 |
| CO | "Company"의 줄임, 레트로 로고 느낌 |
| LINE | 계열·라인업 느낌 |
| CLUB | 소속감, 스트릿웨어에 흔함 |

> **주의**: `WORKS`, `STUDIO`, `CO`, `CLUB` 같은 영어 접미어는 스트릿웨어 업계에서 매우 널리
> 쓰이는 범용 단어다(특정 브랜드의 고유 표현이 아님). 다만 최종 후보를 화면에 내보내기 전,
> 코드화 단계에서 "실존 상표와 똑같은 전체 조합"이 나오지 않는지 가벼운 금지 단어 필터를
> 하나 두는 것을 제안한다(6-3 참고) — 완벽한 상표 검색은 아니지만 최소한의 안전장치는 둔다.

## 6. 손님의 선택권 — 항상 함께 두는 것

선언문 "AI 는 도구다. 추천은 출발점일 뿐이고, 마지막 선택은 사용자가 한다"를 그대로 기능으로
옮기면:

1. **후보 3개 이상은 항상 서로 다른 축에서 최소 하나씩 나온다.** 세 개 다 같은 축이면 "다른
   방향"이 아니라 "같은 방향의 변주"가 된다.
2. **"다시 뽑기" 버튼** — 같은 story 로 다른 조합을 다시 보여준다(사전 안에서 다른 치환 단어·
   접두어/접미어를 골라 재조합).
3. **"내가 직접 쓰기" 입력창은 후보 목록과 항상 같은 화면에, 후보들과 동등한 위치에 둔다.**
   후보 아래 작게 붙는 "기타" 취급이 아니라, 선택지 중 하나로 보이게 한다 — "추천은 출발점"
   이라는 원칙이 화면에서도 보이도록.
4. 후보를 고른 뒤에도 **글자를 고칠 수 있어야 한다**(완전히 새로 쓰는 게 아니라 후보를 바탕으로
   다듬는 중간 단계). 이건 화면/상태 설계가 필요해 이 문서 범위 밖이지만 원칙으로 남긴다.

### 7-1. 시험에서 드러난 문제 — "키워드 없음" 케이스 (20개 중 3개, 15%)
샘플 3·8·15 ("그냥 좋아서요", "ㅎㅎ 그냥 멋있어서 샀어요", "그냥 생각나서")처럼 **명사형
키워드가 없는 짧은 구어체 문장**이 생각보다 자주 나올 수 있다. 이 경우 네이밍 자체가 막힌다.
대응안 두 가지를 제안한다(코드화 단계에서 결정):
- (a) 접두어/접미어 사전만으로 "일반 후보"를 보여준다 (예: `OWN HUE`, `DAY ONE`처럼 서비스
  정체성 쪽 단어를 핵심 단어로 대신 쓴다).
- (b) "조금 더 적어주면 더 잘 맞는 이름을 만들 수 있어요"처럼 **다시 물어보는 재질문**을 한
  번 제안한다. 다만 손님이 이미 "건너뛰기"를 선택할 수 있는 질문이라, 강요처럼 느껴지지
  않게 "괜찮아요, 건너뛸 수도 있어요"를 항상 같이 둔다.
- 개인 의견: (b)가 선언문 기준(AI가 대신 정하지 않고 손님 생각이 담기게)에 더 맞는다고 본다.
  다만 두 번 묻는 건 대화 흐름을 늘리는 일이라, 디자이너·PM 과 같이 판단할 사안으로 남긴다.

### 7-2. 시험에서 드러난 문제 — 사전 표제어와 실제 입력의 불일치
샘플 11("불꽃")이 사전 표제어("불")와 정확히 일치하지 않아 치환이 안 되는 문제가 나왔다.
**부분 일치(포함 관계) 매칭**을 추가하는 것을 제안한다 — 예: 토큰에 사전 표제어가 **포함**
되어 있으면(앞뒤에 다른 글자가 붙어 있어도) 그 표제어의 치환 규칙을 적용. "불꽃"은 "불"을
포함하므로 "불"의 치환 규칙("불씨, 화염 / FLAME, EMBER, SPARK")을 그대로 쓸 수 있다. 다만
이 방식은 오매칭 위험도 있다("불안"에 "불"이 포함되지만 뜻이 다르다) — 코드화 단계에서
"포함되지만 뜻이 다른 예외 목록"을 같이 관리해야 한다. (11-01: 이 규칙을 실제로 코드화
가능한 수준까지 구체화한 의사코드와 예외 목록은 **9절**에 정리했다.)

### 7-3. 축별 체감 — 어느 축이 가장 안정적이었나
- **축1(직설적)**: 20개 중 "키워드 없음" 3개를 빼면 17개 전부 자연스럽게 작동했다. 가장
  안정적이고, 사전 의존도가 가장 낮다(접두어/접미어만 있으면 됨).
- **축2(은유적)**: 핵심 단어가 치환 사전에 없으면(샘플 13, 20) 품질이 눈에 띄게 떨어진다
  (치환 없이 그대로 쓰거나, 아예 생략해야 함). 사전 범위를 넓히는 게 가장 중요한 다음 과제.
- **축3(영어조합)**: 영어 사전이 가장 좁아서(한국어 사전보다 단어 수가 적음) 치환 실패 시
  "직역"(샘플 13, 20처럼 "MY LIFE", "MY SUNSET")으로 떨어지는데, 직역도 나쁘지 않게
  들리는 경우가 의외로 많았다(영어는 직역해도 "브랜드명 같은 느낌"이 어느 정도 유지됨).
  한국어 축2보다 사전 부족의 티가 덜 난다.

## 8. 포함 관계 매칭 — 코드화 가능한 수준의 규칙 (11-01 추가)

7-2절에서 제안으로만 남겼던 "사전 표제어가 입력 토큰에 포함되어 있으면 치환 규칙을 그대로
적용한다"를 실제로 코드로 옮길 수 있는 수준까지 구체화한다. **이 절도 아직 설계다 — 코드는
건드리지 않았다.** 트리거 조건이 충족된 뒤 2절(키워드 추출)·3절(치환 사전) 로직과 함께
`app/` 안의 순수 JS 함수로 옮길 때 이 의사코드를 참고하면 된다.

### 8-1. 왜 필요한가 (다시 정리)
완전 일치만으로는 "불꽃", "하늘색", "새벽빛"처럼 표제어에 접사·수식어가 붙은 흔한 한국어
합성어를 전부 놓친다. 샘플 11("불꽃")이 실제로 이 문제를 보여줬다. 반대로 포함 관계를
무조건 허용하면 "불안"에 "불"이 끼어드는 것처럼 뜻이 전혀 다른 단어까지 잘못 치환된다
(7-2절). 그래서 "포함되면 매칭"과 "그런데 예외는 분명히 걸러낸다"를 한 쌍으로 설계한다.

### 8-2. 매칭 순서 — 정확 일치 먼저, 포함 관계는 그다음
```
function findDictionaryEntry(token, dictionary, exceptionList):
  # 1단계: 정확 일치를 항상 먼저 시도한다.
  # (포함 관계 매칭보다 우선순위가 높다 — "불"이라는 토큰 자체는
  #  무조건 "불" 표제어로 바로 매칭되어야 하고, 괜히 더 긴 다른
  #  표제어의 부분 문자열인지부터 확인할 필요가 없다.)
  if token in dictionary.headwords:
    return dictionary[token]

  # 2단계: 예외 목록에 토큰이 있으면 포함 관계 매칭을 시도하지 않고
  # 즉시 "치환 없음"으로 끝낸다. (오매칭을 막는 가장 확실한 장치)
  if token in exceptionList:
    return null   # 치환하지 않고 원래 단어 그대로 쓴다 (3-3절 치환 원칙)

  # 3단계: 포함 관계 매칭. 표제어 길이가 긴 것부터 먼저 비교한다.
  # (예: 표제어 "새벽"과 "벽"이 둘 다 있다고 가정하면, "새벽빛"이라는
  #  토큰에서 더 의미 있는 쪽인 "새벽"을 "벽"보다 먼저 찾아야 한다.
  #  짧은 표제어가 긴 표제어 안에 우연히 끼어들어 먼저 걸리는 걸 막는다.)
  candidates = dictionary.headwords
    .filter(headword => token.includes(headword))
    .sort(by: headword.length, order: 'desc')

  for headword in candidates:
    # 4단계: 표제어가 토큰의 "맨 앞" 또는 "맨 뒤"에 붙어 있을 때만
    # 인정한다. 단어 중간에 끼어 있는 경우는 인정하지 않는다.
    # (한국어 합성어는 보통 어근이 앞/뒤에 붙는 형태라 이 조건으로
    #  대부분의 자연스러운 합성어는 잡고, 우연한 끼어듦은 줄어든다.
    #  예: "불꽃" → "불"이 맨 앞 → 인정. "모닥불" → "불"이 맨 뒤 → 인정.
    #      "불안"도 맨 앞이라 이 조건만으로는 걸러지지 않음 — 그래서
    #      2단계 예외 목록이 반드시 같이 있어야 한다.)
    if token.startsWith(headword) or token.endsWith(headword):
      # 5단계: 표제어를 뺀 나머지 글자 수가 1글자뿐이면 보수적으로
      # 한 번 더 확인한다(짧을수록 오매칭 비율이 높다는 걸 7-2절
      # 샘플에서 체감했다) — 나머지 글자가 exceptionList 의 "접두/
      # 접미 조각" 목록에 있으면 제외.
      remainder = token.replace(headword, '')
      if remainder.length <= 1 and remainder in exceptionList.fragments:
        continue
      return dictionary[headword]

  return null  # 포함 관계로도 못 찾음 → 사전 밖 단어, 그대로 쓴다
```

### 8-3. 오매칭을 막기 위한 예외 목록 (초안)
아래 두 종류로 나눠 관리한다. 실제 코드화 시점에 사전과 같은 자리(별도 JSON/JS 객체)에
둔다.

**(A) 통째로 예외 처리할 토큰** (`exceptionList.tokens`) — 표제어를 포함하지만 뜻이
전혀 달라 포함 관계 매칭을 시도조차 하지 않아야 하는 단어:

| 토큰 | 포함된 표제어 | 왜 예외인가 |
|---|---|---|
| 불안 | 불 | "불안"은 불(火)과 무관한 감정 단어 |
| 불편 | 불 | 부정 접두사 "불-"(不)이지 화염의 "불"이 아님 |
| 불가능 | 불 | 위와 같음 (不-) |
| 바다표범 | 바다 | 동물 이름 고유어라 "바다"의 치환 뜻(파도·수평선)과 안 맞음 |
| 걸음걸이 | 걸음 | 표제어 자체의 반복 변형이라 치환하면 "걸음걸이씩" 류로 어색해짐(접미어 결합 시 이중 접사 위험) — 치환 자체는 틀리지 않지만 결과 품질이 낮아 제외 |
| 길이 | 길 | "길이"는 "거리/length"의 뜻이지 "길(street, 道)"이 아님 — 조사 "이"가 아니라 단어 자체가 다름 |
| 다름없이 | 다름 | 부사형 관용구라 치환하면 뜻이 깨짐 |
| 새벽잠 | 새벽 | 포함은 맞지만 "잠"이 핵심이라 치환하면 엉뚱한 방향("여명 잠" 등)이 됨 — 길이 조건(8-2 5단계, remainder 1글자 아님)만으로는 못 걸러서 토큰 전체를 예외로 추가 |

**(B) 짧은 나머지 글자 조각** (`exceptionList.fragments`) — 8-2 5단계에서 쓰는,
표제어를 뺀 나머지가 1글자일 때 함께 확인하는 목록. 아래 글자가 나머지라면 매칭을
취소한다:

| 나머지 글자 | 예시 토큰 | 왜 예외인가 |
|---|---|---|
| 안 | 불안 (표제어 "불" + 나머지 "안") | (A)에도 있지만 유사 패턴 재발 방지용으로 조각 단위로도 등록 |
| 편 | 불편 | 위와 같음 |
| 이 | 길이, 색이 | 조사·명사화 접미사 "-이"가 뜻을 바꾸는 경우가 많음 |
| 상 | 불상, 길상 | "-상(像/相)" 등 한자 접미사가 붙으면 전혀 다른 단어가 됨 |

> (A)와 (B)는 겹치는 경우도 있다(예: "불안"은 둘 다에 흔적이 있음) — 의도적 중복이다.
> (A)는 "토큰 전체를 안다"는 확실한 경우를 빠르게 막고, (B)는 (A)에 없는 새로운 토큰이
> 나와도 "짧은 나머지 글자" 패턴만으로 1차 방어가 되게 하는 안전망이다. 두 목록 모두
> 지금은 **추측으로 채운 초안**이다 — 실제 손님 입력이 쌓이면 새로 발견되는 오매칭
> 사례를 계속 추가해야 한다(9절 "다음에 할 것" 참고).

  과도하게 막을 위험이 있다고 판단**했다. 이 단어들은 표제어가 1글자(별·달·비·눈·산·나무·돌·강)
  라서 애초에 1글자 표제어는 포함 관계 매칭의 오매칭 비율이 구조적으로 높다는 뜻으로 보고,
  개별 토큰 예외 추가보다 **8-5절의 한계로 기록하고 다음 단계(코드화 시점)에서 "1글자
  표제어는 포함 관계 매칭 자체를 적용하지 않는다"는 규칙 추가를 검토하는 쪽을 제안한다
  (8-4절 참고 — 지금은 "2글자 이하 토큰"만 적용 제외 대상이고 "1글자 표제어"는 별도
  규정이 없다. 이 문서 8-7절에 신설).
- 강·산·나무·돌·비·눈·달·별은 모두 1글자 표제어이고, 한국어에서 1글자 명사는 다른 단어의
  일부로 쓰이는 경우가 2글자 이상 표제어보다 훨씬 많다(조어력이 높다) — 그래서 이 여덟
  단어는 개별 오매칭 토큰을 일일이 예외 목록에 추가하는 방식보다 구조적 규칙(8-7절)으로
  다루는 게 더 안전하다고 판단했다.

### 8-4. 포함 관계 매칭을 적용할 때와 적용하지 않을 때
- 축1(직설적)에는 적용하지 않는다 — 축1은 "손님이 쓴 단어를 거의 그대로" 쓰는 것이 원칙
  (4절)이라, 치환 사전과 무관하게 입력 토큰 자체를 그대로 쓴다. 포함 관계 매칭은
  **축2(은유적)·축3(영어조합)에서 치환 단어를 찾을 때만** 적용한다.
- 2글자 이하 토큰에는 적용하지 않는다(2-2절의 "두 글자 이하 토큰은 자르지 않는다" 규칙과
  같은 이유 — 너무 짧으면 포함 관계 자체가 의미 없어진다. 표제어 자체가 2글자인 경우
  정확 일치로 이미 1단계에서 잡힌다).
- 사용자에게 보여줄 설명 문구("너의 '불꽃'에서 번져 나온 이름")에는 **포함 관계로 찾았다는
  사실을 숨기지 않는다** — 원래 토큰("불꽃") 그대로 설명에 쓰고, 치환은 표제어("불")의
  규칙을 썼다는 점은 화면에 노출하지 않아도 되지만 내부적으로는 구분해 둔다(나중에
  오매칭 신고가 들어왔을 때 원인 추적이 쉬워지도록).

### 8-5. 이 설계의 한계
- 이 예외 목록은 실제 손님 입력을 하나도 보지 않고 **추측으로 만든 초안**이다(8-3절의
  모든 단어는 신 브랜더가 "있을 법한 오매칭"을 상상해서 채운 것). 실제 story 답변이
  쌓이면 지금 목록엔 없는 새로운 오매칭이 분명히 나올 것이고, 지금 목록에 있는 항목이
  실제로는 한 번도 안 나올 수도 있다.
- 형태소 분석기 없이 문자열 포함·접두/접미 비교만으로 판단하기 때문에, 한국어의 모든
  합성어 규칙을 다 반영하지 못한다. "어느 정도 걸러내는 안전장치"이지 완벽한 언어 분석이
  아니라는 점을 코드화할 때도 그대로 가져가야 한다.

### 8-6. 동음이의어는 예외 목록으로 해결 안 됨 (11-06 추가)
"경계"처럼 **한자가 다른 동음이의어**(境界 vs 警戒)는 포함 관계 매칭뿐 아니라 **정확
일치**(8-2절 1단계)에서도 원래 위험하다 — 손님이 "경계"라고만 썼을 때 그게 境界(가장자리)
뜻인지 警戒(주의) 뜻인지는 문자열만으로는 구분할 수 없다. 이 문제는 포함 관계 매칭의

## 10. developer 검토 (2026-11-03 추가)

신 브랜더가 10-29·11-01 두 차례 "팀원에게 한마디"에서 남긴 두 질문에, **실제 `app/app.js`·
`backend/Code.gs` 코드를 읽고** 답한다. 이 절도 코드화는 아니다 — `app/`, `backend/` 는
오늘 전혀 건드리지 않았다. 코드화 시점에 이 절을 그대로 참고하면 된다.

### 10-1. 질문 ① — story 입력값을 네이밍 함수에 그대로 넣어도 안전한가

**결론: 지금 들어오는 story 값 자체는 이미 꽤 정리된 상태라, 네이밍 함수가 추가로 걱정해야
할 범위는 생각보다 좁다.** 코드로 확인한 사실은 다음과 같다.

- **화면(`app/app.js`)의 입력 단계**: `QUESTIONS.story.parse()`(app.js 259-263행)가
  `cleanText(raw, 1, 200)`(1150-1153행)를 거친다. `cleanText` 는
  `replace(/[ -]/g, ' ')` 로 제어문자를 공백으로 바꾸고, 연속 공백을 하나로
  줄이고, 양끝 trim 한 뒤 **1~200자**인지 검사한다. 200자를 넘거나 정리 후 빈 문자열이면
  `{ error: ... }` 를 돌려주고 화면은 그 값을 아예 다음 단계로 넘기지 않는다 — 즉 **200자를
  넘는 story 가 `chat.data.story` 에 들어갈 길 자체가 지금 화면 코드에는 없다.**
- **서버(`backend/Code.gs`)의 재검증**: `cleanText_(body.story, STORY_MAX)`(Code.gs 162행,
  `STORY_MAX = 200`, 62행)가 화면과 거의 같은 규칙(제어문자 제거, 공백 정리, 길이 제한)을
  **서버 쪽에서 다시** 적용하고, `v.length > max * 4` 면 즉시 `null`(저장 거부)로 처리한다
  (416-422행). 화면 쪽 검증을 손님이 우회해서 서버에 긴 값을 보내도 서버가 한 번 더 막는다는
  뜻이다. 네이밍 기능은 story 가 **저장된 뒤**(즉 서버 검증을 통과한 뒤) 돌게 될 거라
  이 단계를 신뢰할 수 있다.
- **화면 출력은 `textContent`만 쓴다 — `innerHTML` 사용처가 코드 전체에 없다.** `el()` 함수
  (app.js 1273-1278행) 자체가 `n.textContent = text` 로만 동작하고, story 를 보여주는
  접수완료 화면(859-861행, `el('p', 'done-story', '"' + chat.data.story + '"')`)도 이
  `el()` 을 거친다. `grep -n "innerHTML" app/app.js` 결과가 0건이다 — **지금 코드 구조상
  story 값에 `<script>` 같은 HTML/JS 를 넣어도 화면에 문자 그대로("<script>...")만 찍히고
  실행되지 않는다(DOM 삽입 경로에서의 XSS 는 현재 없음).**
- **서버 전송은 `JSON.stringify` 로 이스케이프된다.** `postRequest()`(app.js 737-754행)가
  `body: JSON.stringify({ ..., story: pending.data.story || '', ... })` 로 보낸다.
  `JSON.stringify` 가 인용부호·백슬래시·제어문자를 표준 JSON 이스케이프로 처리하므로,
  story 안에 `"`, `\`, 줄바꿈이 들어 있어도 요청 바디 자체가 깨지지 않는다(인젝션 아님).
  스프레드시트 수식 인젝션(`=`, `+`, `-`, `@` 로 시작하는 값이 셀에서 수식으로 해석되는
  문제)도 서버의 `safeCell_()`(Code.gs 445-447행)가 앞에 `'` 를 붙여 이미 막고 있다 —
  story 를 포함한 모든 자유 입력 칸에 공통으로 적용된다.
- **네이밍 함수 관점에서 실제로 남는 위험**: 위 세 겹(화면 1~200자 제한 → 서버 재검증 →
  textContent 출력)을 통과해 네이밍 함수에 들어오는 story 는 "제어문자 없는, 공백이 정리된,
  1~200자 한국어/영어 혼용 텍스트"로 봐도 된다. 다만 **이모지는 지금 걸러지지 않는다** — 7절
  설계 문서(2-1절)는 "이모지 제거"를 전제하지만, `cleanText`/`cleanText_` 는 이모지를 지우지
  않는다(제어문자 범위 ` -` 와 공백만 처리 — 이모지는 그 범위 밖이다).
  **확인한 사실**: 이모지가 섞인 story(예: "나의 색🔥")가 화면·서버 검증을 모두 통과해
  `chat.data.story` 에 그대로 남는다. 코드화 시점에 2-1절의 "이모지 제거"를 실제로 구현하려면
  네이밍 함수 쪽(토큰화 전처리)에서 별도로 이모지를 걸러내는 정규식을 추가해야 한다 — 지금
  `cleanText` 를 재사용하는 것만으로는 안 된다는 뜻이다. **무한루프 가능성**: 8-2절 의사코드의
  `token.includes`/`startsWith`/`endsWith` 는 모두 자바스크립트 표준 문자열 메서드로, 입력
  길이에 비례해서만 시간이 걸리고 루프 종료 조건이 입력 밖에 있지 않으므로(사전 배열을
  순회하는 `for` 문 — 사전은 유한하다) 어떤 입력에도 무한루프에 빠질 구조적 위험은 없다고
  판단한다. 다만 이건 "8절 의사코드를 그대로 코드화했을 때"의 판단이고, 실제 구현이 달라지면
  다시 봐야 한다.
- **종합 답변**: story 를 네이밍 함수에 "그대로" 넣어도 XSS·인젝션·과도한 길이 쪽은 지금
  화면+서버 구조가 이미 막고 있어 **추가 방어선을 겹겹이 새로 쌓을 필요는 없다.** 다만
  (a) 이모지 제거는 네이밍 전처리 단계에서 별도로 구현해야 하고(기존 함수가 안 해준다),
  (b) 네이밍 함수를 **서버 검증을 거치지 않은 값**(예: "다시 뽑기" 버튼이 사용자가 입력 중인
  값을 즉시 미리보기로 돌리는 식으로 설계된다면)에 적용할 가능성이 생기면 그때는 화면 쪽
  `cleanText` 결과만 믿지 말고 네이밍 함수 입구에서 한 번 더 길이·공백 정리를 자체적으로
  하는 걸 권한다 — 지금은 story 가 최종 저장되기 전 단계라 가정이 아직 코드로 확정되지
  않았으므로, 이 부분은 "코드화 시점에 다시 확인 필요"로 남긴다(확인 못함).

### 10-2. 질문 ② — 8절 포함 관계 매칭이 사전이 커지면 느려지는가

**결론: 지금 추정되는 입력 크기(최대 200자, 사전 수백 개)에서는 브라우저 성능 문제가 될
가능성이 매우 낮다.** 정확한 벤치마크 대신 Big-O 추정과 실제 입력 조건으로 가늠한다.

- **8-2절 의사코드의 시간 복잡도**: 토큰 하나당 ① 정확 일치는 `Set`/객체 조회면 O(1),
  ② 포함 관계 매칭은 `dictionary.headwords.filter(... token.includes(headword))` 로 사전
  **전체**를 순회(O(사전 크기 N)), 그 안에서 `token.includes`/`startsWith`/`endsWith` 는
  각각 O(토큰 길이 L) — 결국 토큰 하나당 **O(N × L)**. story 전체(토큰 K개)에 대해
  **O(K × N × L)**.
- **실제 값 추정**: story 는 최대 **200자**(`QUESTIONS.story.input.maxlength`, app.js 257행
  / `STORY_MAX`, Code.gs 62행 — 둘 다 코드로 확인됨). 토큰은 공백 기준 분리(2-1절)이므로
  한국어 한 줄 문장에서 K는 많아야 수십 개(공백 하나 없는 극단적 입력이라도 L ≤ 200이라
  토큰 수는 사실상 1개). 지금 사전(3-1·3-2절 표제어)은 약 33개, "장차 수백 개"로 커진다고
  가정해도 N ≤ 1000 정도로 보는 게 합리적이다(한국어 일상어 사전이 그 이상으로 비대해지면
  오히려 3-3절 "선택 피로" 원칙에 어긋나 사전 자체를 그렇게 키우지 않을 가능성이 높다).
  표제어 하나의 길이도 실제 사전을 보면 1~5자 수준(예: "다름없이"가 가장 길다, 4자)이라
  L(표제어 길이)은 사실상 상수로 봐도 된다 — `startsWith`/`endsWith` 비교 자체도 짧은
  문자열끼리의 비교라 사람이 느낄 수 있는 지연과는 거리가 멀다.
- **대략적인 연산 횟수**: K(토큰 수, 최대 수십) × N(사전 크기, 최대 약 1000) × 비교 2회
  (`startsWith`+`endsWith`) ≈ 최악의 경우에도 **수만 번의 문자열 비교** 수준. 최신 모바일
  브라우저의 JS 엔진은 이런 단순 문자열 비교를 초당 수백만~수천만 번 처리하므로, 체감
  지연(예: 100ms 이상)이 생기려면 사전이 지금 추정치보다 몇 자릿수는 더 커져야 한다. 손님이
  버튼을 눌러 "다시 뽑기"를 할 때마다 다시 계산해도 마찬가지로 체감되지 않을 정도로 본다.
- **정확한 벤치마크는 하지 않았다 — 확인 못함.** 실제 모바일 기기(특히 저가형 안드로이드,
  인앱 브라우저)에서 실측한 수치는 없다. 다만 Big-O 추정과 지금까지 나온 사전·입력 크기
  추정치를 종합하면, "포함 관계 매칭을 반복문으로 돌리는 구조" 자체가 문제가 될 가능성보다는
  **사전이 지금 추정(수백 개)보다 훨씬 커지거나(예: 수만 개), story 가 지금 200자 제한을
  벗어나는 식으로 전제가 바뀌는 쪽이 먼저 문제가 될 가능성이 높다** — 지금 전제가 유지되는
  한 성능보다는 "오매칭 정확도"(8-3·8-5절)가 더 중요한 과제로 본다.
- **그래도 미리 생각해 둘 대안** (사전이 예상보다 훨씬 커질 경우를 대비해 기록만 남김,
  지금 당장 적용을 제안하는 건 아니다):
  1. **표제어를 길이별로 미리 묶어 둔다** — 8-2절 3단계가 이미 "표제어 길이가 긴 것부터"
     정렬하므로, 정렬을 매번 하지 않고 사전을 애초에 길이 내림차순 배열로 저장해 두면
     `.sort()` 호출(O(N log N))을 없앨 수 있다. 지금 의사코드는 매 토큰마다 `filter` 뒤
     `sort` 를 다시 하므로, 이 부분만 사전 로드 시 한 번 정렬해 두는 것으로 바꿔도 코드
     변경은 작고 효과는 있다.
  2. **정확 일치(1단계)를 `Map`/객체로 이미 하고 있는 것처럼, 포함 관계도 표제어를 접두사
     트라이(trie)로 구성하면** 토큰 길이에만 비례하는 매칭이 가능하지만, 지금 사전 크기
     추정(수백 개)에서는 구현 복잡도 대비 이득이 거의 없다 — "사전이 수천~수만 개로 커지는
     일이 실제로 생기면" 그때 고려할 선택지로만 남긴다.
  3. 가장 간단한 안전장치는 **story 길이 제한(이미 200자)과 사전 크기에 상한을 두는 것**이다
     — 둘 다 이미 사실상 존재하거나(200자) 디자인 원칙(3-3절 선택 피로 방지)으로 자연히
     억제되고 있어서, 별도 장치를 추가하지 않아도 지금 설계가 스스로 상한을 두고 있다고 본다.

### 10-3. 요약

| 질문 | 답 |
|---|---|
| ① story 를 그대로 네이밍 함수에 넣어도 안전한가 | 화면 입력 제한(200자) + 서버 재검증(`cleanText_`) + `textContent` 출력 + `JSON.stringify` 전송 + `safeCell_` 수식 방지, 이 다섯 겹을 코드로 확인했다. XSS·인젝션·과도한 길이 쪽은 지금 구조로 충분하다. 다만 이모지 제거는 기존 함수가 안 해주므로 네이밍 전처리에서 별도 구현 필요. 네이밍 함수가 "서버 검증 전" 값을 다루게 될 가능성은 코드화 시점에 다시 확인 필요(확인 못함). |
| ② 사전이 커지면(수백 개) 느려지는가 | Big-O 로는 토큰당 O(N×L), 실제 입력 조건(200자, 사전 ~수백~1000개, 표제어 길이 ~1~5자)에서는 최악의 경우도 수만 번의 문자열 비교 수준이라 모바일 브라우저에서 체감 지연이 생길 가능성은 낮다고 판단한다. 정확한 실측 벤치마크는 하지 않았다(확인 못함). 사전이 수만 개 이상으로 커지는 극단적 상황이 오면 trie 구조나 사전 사전정렬 같은 대안을 그때 고려하면 된다. |
