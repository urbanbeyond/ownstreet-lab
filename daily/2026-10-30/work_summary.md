# Day — developer

## 오늘 한 것
`daily/2026-10-30/pm_decision.md`, `ROADMAP.md`, `daily/2026-10-26/pm_decision.md`(10-26 회의
결정 전문), `daily/2026-10-28/work_summary.md`(chat.active 전수조사 마무리 기록)를 먼저 읽어
오늘 과제의 배경을 확인했다. 오늘 목표는 **이탈 로그 설계 검토**(구현 아님) — ROADMAP Stage 1
에 10-11부터 "방법 미정"으로 남아 있던 가장 오래된 미해결 안건을 처음으로 정면에서 다루는 날.

1. **현재 흐름 전수 파악**: `app/app.js`(1309줄) 전체, `backend/Code.gs`(489줄), `app/config.js`,
   `backend/API.md` 를 다시 읽고 사용자가 밟는 단계(진입 → url → story → size → 로그인 →
   name → phone → address → memo → confirm → placeOrder → 서버 응답 → 완료)와, 지금 가진
   세 가지 수단이 실제로 무엇을 아는지 정확히 짚었다.
   - **서버 시트 줄**(`REQUESTS`): `processRequest_()` 가 저장 후 "다시 읽어 확인"까지 끝낸
     경우에만 한 줄이 생긴다(222~231행). 즉 **완료된 요청만** 안다.
   - **`sessionStorage` draft**(`DRAFT_KEY`, `app.js` 1078~1100행): 그 손님의 그 탭에만 있고
     서버로 전송되지 않는다. 탭을 닫거나 로그아웃(`clearSessionData()`)하면 사라진다.
   - **브라우저 콘솔**(`console.info/warn/error`, 9곳): 그 손님의 개발자 도구에만 찍히고
     팀이 원격으로 모을 방법이 없다.
   - `backend/API.md` 7절에 이미 "내 주문 조회, 상태 변경, 이탈 기록은 아직 없다"가 명시돼
     있는 것도 확인했다(오늘 검토와 결이 같다).
2. **핵심 사실 확인**: 위 세 수단 중 어느 것도 "팀이 나중에 모아서 볼 수 있는, 중간에 그만둔
   세션의 집계"를 만들지 못한다. 서버는 완료만 알고(분자는 있음), 분모(시작한 세션 수)를 전혀
   모른다. 이건 설계를 더 다듬어서 풀 수 있는 문제가 아니라 구조적으로 막혀 있는 것이라고
   판단했다 — 서버가 모르는 일은 서버가 셀 수 없다.
3. **네 가지 대안 검토 후 기각/보류 이유 정리**:
   - (A) 서버에 새 "세션 시작" 신호(ping) 추가 → 분모를 만들 수 있는 유일한 방법이지만
     `Code.gs` 수정 + 의장 배포가 필요해 오늘 범위(코드 변경 없음) 밖. 다음에 쓸 설계 초안으로
     문서에 남김.
   - (B) 시트의 "저장은 됐지만 재확인 실패"로 남은 줄을 읽기 → 스프레드시트를 열어봐야 하는
     방법이라 AI 팀 규칙(고객 데이터 접근 금지)과 충돌, 그리고 로그인조차 못 한 이탈은 못 잡음.
   - (C) `sessionStorage` 를 `beforeunload` 로 서버에 보내기 → 모바일(특히 iOS Safari, 인앱
     브라우저)에서 발화 신뢰도가 낮아 구조적으로 측정이 실제보다 적게 잡힘. 이것도 서버 수정 필요.
   - (D) 외부 분석 서비스(GA, Mixpanel 등) → 10-26 회의에서 이미 기각된 것과 같은 이유로
     원칙상 계속 배제. 제안으로만 남긴다.
4. **결과를 `docs/funnel-drop-off-design.md` 로 정리**: 위 전수 파악·핵심 사실·네 대안 비교에,
   "다음에 구현한다면"의 최소 초안(새 액션 `ping`, 단계 이름만 담은 1회성 비차단 `fetch`,
   날짜별 집계 시트)과 그 초안의 한계(세션 식별자 없이 가므로 정확한 세션 추적이 아니라
   "대략의 깔때기 모양"만 본다는 것)까지 미리 적어 뒀다. 코드는 쓰지 않았다 — 설계 문서 안의
   예시 설명일 뿐 저장소에 실제로 들어간 코드는 없다.
