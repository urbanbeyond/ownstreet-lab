## 오늘 한 것

오늘의 일은 서버(`backend/Code.gs`)를 v2 로 고치는 것이었다. 새 대화형 화면이 사이즈와 주소를 보내도 서버가 받아 줄 수 있게 하되, 지금 LIVE 에서 쓰는 v0 폼의 요청도 그대로 받는다.

**서버 (Code.gs v2)**
- `doGet` 이 `version: 2` 를 돌려준다. 같이 `storage`(저장할 시트를 열 수 있는지)와 `ready`(키와 저장소가 모두 준비됐는지)를 알려 준다. `ready` 의 뜻이 조금 바뀌었다 (이전에는 키만 봤다. 아래 "뒤집을 수 있는 결정" 참고).
- 요청에 `v` 가 없으면 옛 형식(이름·전화번호·URL)으로 받는다. `v: 2` 면 새 형식으로 받는데, 사이즈(S, M, L, XL, 2XL, 3XL)와 주소(5~200자)가 필수이고 배송 요청(300자까지)과 한 줄 이야기 `story`(200자까지)는 선택이다. 옛 형식 요청에 이 항목들이 따라오면 있는 것만 검증해서 저장한다. 서버가 모르는 더 큰 `v`(3 이상)는 `VERSION_MISMATCH` 로 거절한다. 모르는 항목을 조용히 버리고 "접수됐다"고 하는 일을 막기 위해서다.
- `address`, `memo`, `story` 에도 `safeCell_` 을 적용했다 (이름·URL 은 원래 했다).
- 시트 열: 기존 7칸(접수번호~상태)은 그대로 두고, 상태 뒤에 사이즈 / 주소 / 배송 요청 / 한 줄 이야기 / clientRef / 동의 시각 6칸을 덧붙였다. 이미 머리글이 있는 시트에는 빈 칸만 채운다. 기존 1~7번 칸의 이름이 다르게 바뀌어 있어도 덮어쓰지 않는다. 8~13번 칸에 다른 글자가 이미 있으면 덮어쓰지 않고 접수를 멈춘다(`SERVER_ERROR`와 로그).
- `clientRef` 를 시트에 저장하고, 같은 이메일 + 같은 `clientRef` 가 이미 시트에 있으면 새 줄을 만들지 않고 그 줄의 번호를 돌려준다(`duplicate: true`). 예전에는 캐시에만 있어서 캐시가 사라지면 줄이 중복될 수 있었는데, 이제 시트가 기준이다. 캐시는 더 이상 쓰지 않는다.
- 동의 시각을 저장한다. 서버가 `consent: true` 가 든 요청을 받은 시각이다 (지금은 접수시간과 같은 순간).
- 저장 뒤 다시 읽어 확인하는 범위를 넓혔다. 예전에는 번호와 이메일만 비교했고, 이제는 번호·이메일·사이즈·clientRef·동의 시각을 비교한다. 맨 끝 칸(동의 시각)까지 읽으니 줄이 끝까지 써졌는지도 보게 된다. 어느 하나라도 다르면 접수번호 없이 `SERVER_ERROR` 다.
- 성공 응답에 `v: 2` 를 넣었다.
- 스프레드시트 ID 는 코드에서 없애고 스크립트 속성 `SPREADSHEET_ID` 에서 읽는다. 속성이 없으면 시트에 붙은 스크립트일 때만 그 시트를 쓴다. 속성은 있는데 열 수 없으면 붙은 시트로 몰래 바꾸지 않고 실패한다(엉뚱한 시트에 쌓이는 것을 막으려고).
- 읽다 보니 눈에 띈 것: `Code.gs` 에 `FIREBASE_API_KEY` 의 실제 값이 이미 들어 있다. `app/config.js` 에도 공개되는 Firebase 웹 키라서 비밀값이 아니고, 어제 회의에서도 그렇게 판단했다. 오늘은 그대로 두었다.

## 잘 안 된 것, 아쉬운 것
- **실제 서버에서 돌려 보지 못했다.** 모의 테스트가 161개 통과해도, 진짜 `SpreadsheetApp`, `LockService`, `UrlFetchApp` 가 가짜와 똑같이 움직이는지는 모른다. 특히 아래는 가짜가 내 추측대로 만든 부분이다: 줄 전체에 텍스트 형식을 먼저 걸고 값을 쓰는 순서, 열이 모자란 시트에 `insertColumnsAfter` 로 열을 늘리는 것, 웹 앱 실행 중 `getActiveSpreadsheet()` 가 시트에 붙은 스크립트에서 시트를 돌려주는 것(v0 코드도 같은 호출을 썼다), `'` 로 시작하는 값을 읽었을 때 어떻게 보이는지. 마지막 것은 모르기 때문에 이름·주소 같은 자유 입력은 다시 읽기 비교에서 일부러 뺐다 (대신 맨 끝 칸까지 써졌는지를 본다). 이것이 약점이라는 것은 `API.md` 의 "아직 하지 않는 것"에도 적었다.
- **같은 `clientRef` 로 내용이 다른 요청이 오면 서버는 먼저 저장된 번호를 돌려준다.** 내용이 바뀌면 새 `clientRef` 를 만드는 것은 화면의 일이다(초안은 내용의 서명으로 그렇게 한다). 서버가 내용을 비교하지는 않는다.
- 읽기 확인에서 실패했지만 줄은 시트에 남은 경우, 손님이 다시 시도하지 않으면 그 줄은 `접수` 상태로 시트에 남는다. 손님 화면은 실패였는데 시트에는 있는 주문이 생길 수 있다. 같은 요청을 다시 보내면 그 줄을 찾아 쓰기 때문에 줄이 늘지는 않는다. 이 줄을 표시해 두는 방법(상태 열에 따로 표시)은 오늘 넣지 않았다.
- 시트를 쓰는 중 8~13번 칸에 의장이 다른 내용을 둔 경우 접수가 멈춘다. 데이터를 덮어쓰지 않으려는 선택이다. 의장이 그 칸을 쓰고 있는지 나는 모른다.
- 동의 문구의 "버전"(어떤 문구에 동의했는지)은 아직 저장하지 않는다. 어제 회의에서 내가 짚은 것인데 오늘 범위 밖이어서 넣지 않았다.
- URL 이 PNG 인지 확인하는 방법은 여전히 없다. 오늘 범위도 아니었다.
- 서버를 배포하기 전까지 LAB 의 대화형 화면은 주문을 받을 수 없다. (대화형 화면은 아직 `app/` 에 올라오지도 않았다. 10-11 작업이다. 지금 LAB 은 한 번도 배포된 적이 없고, 오늘 내 기록은 "고쳤다"까지이지 "LAB 에서 돈다"가 아니다.)

## 의장이 확인할 것

### 확인 1. 서버가 v2 로 응답하는가
- **무엇을**: LAB 서버 주소를 열었을 때 버전이 2 로 나오는지.
- **어디서**: LAB Apps Script 의 웹 앱 `.../exec` 주소 (Apps Script 오른쪽 위 배포 → 배포 관리에서 보이는 URL). 절차는 `OPERATOR_TODO.md` A-7.
- **어떻게**: 브라우저 주소창에 그 주소를 열고, 화면에 나오는 한 줄 글자를 본다. 고객 데이터는 나오지 않는다.
- **정상일 때**: `"version":2`, `"ready":true`, `"storage":true` 가 모두 보인다.
- **틀리면**: `version` 이 없으면 새 버전 배포를 안 한 것(또는 배포를 새로 만들어 주소가 달라진 것). `"storage":false` 면 시트 ID 속성이 틀린 것. 나온 글자를 `DIRECTION.md` 에 적어 주세요 (ID·키 값은 빼고).
- **내가 확인하지 못한 것**: 실제 서버에서 이 주소를 열어 보지 못했다. 가짜 환경에서 `doGet` 이 위 모양을 돌려주는 것만 확인했다.

### 확인 2. 새 열이 상태 열 뒤에 붙었고 기존 열 순서가 그대로인가
- **무엇을**: 시트 첫 줄(머리글)이 13칸이고, 앞 7칸이 예전 그대로인지.
- **어디서**: LAB 스프레드시트 `ownstreetdb-LAB` 의 `REQUESTS` 탭 첫 줄. (LIVE 는 B-3 에서 머리글만 본다.)
- **어떻게**: `setup` 을 실행한 뒤(OPERATOR_TODO A-5) 첫 줄을 눈으로 본다. 고객 줄은 열 필요 없다.
- **정상일 때**: `접수번호 | 접수시간 | 이메일 | 이름 | 전화번호 | URL | 상태` 다음에 `사이즈 | 주소 | 배송 요청 | 한 줄 이야기 | clientRef | 동의 시각`. 총 13칸 (A~M).
- **틀리면**: 칸 이름이나 순서가 다르면 그 모양 그대로 `DIRECTION.md` 에 적어 주세요. LIVE 에서 `setup` 이 "머리글 충돌"을 내면 H 열 이후에 의장이 쓰던 칸이 있다는 뜻이다. 서버는 덮어쓰지 않고 멈춘다.
- **내가 확인하지 못한 것**: 진짜 구글 시트에서 머리글이 채워지는 것을 보지 못했다. 가짜 시트에서 (빈 시트 / 7칸 머리글과 옛 줄이 있는 시트 / 열이 7개뿐인 시트 / 8번째 칸에 다른 글자가 있는 시트) 네 경우를 확인했다.

### 확인 3. 시트 ID 를 넣는 곳 (스크립트 속성)
- **무엇을**: 스프레드시트 ID 가 코드에 없고 스크립트 속성에서 읽히는지.
- **어디서 넣나**: Apps Script 왼쪽 ⚙ 프로젝트 설정 → 맨 아래 스크립트 속성 → 속성 `SPREADSHEET_ID` (값은 시트 주소의 `/d/` 와 `/edit` 사이 긴 글자). 절차는 `OPERATOR_TODO.md` A-4.

- 초안의 `REQUEST_TIMEOUT_MS` 를 60초로 (초안은 `ensureServer` 의 GET 에도 같은 한도를 쓴다. GET 은 짧게 따로 두는 쪽이 낫다).
- `submitOrder` 가 `TIMEOUT`, `NETWORK`, `BAD_RESPONSE`, `HTTP_*` 에서 바로 `handleResult` 의 "접수에 실패했습니다"로 가지 않게, 같은 `clientRef`(`state.pending`)로 한 번 더 확인한 뒤 "접수됐는지 아직 확인하지 못했습니다" + "다시 확인 / 카톡 문의".
- 초안의 "다시 시도" 버튼(`retryBtn`)은 "다시 확인"으로. 초안의 `chat.data` 를 고쳐서 다시 보내면 `sig` 가 달라져 새 `clientRef` 가 생긴다. 접수 여부를 모르는 상태에서는 이전 요청을 먼저 확인한다 (v0 화면의 `settleOldPending` 과 같은 방식).
- 임시 저장(sessionStorage)에 `clientRef` 포함 (위 한계 참고).
- 접수 성공 판정은 `ok === true` + `OS-` 번호 + `v >= 2` 세 가지 모두.
- 로그아웃·"처음부터"에서 지우는 것과 모순되지 않게: 접수 여부를 모르는 `clientRef` 는 지우기 전에 한 번 확인하거나, 지우면 중복 가능성을 손님에게 알릴지 월요일 회의에서 정한다.

### 일정에 대해
- 이 수정을 오후에 끝냈다 (화면의 한 함수 흐름과 서버 로그). PM 결정의 "오늘 안에 못 끝났을 때" 조건(①-1~4 미완, ⑤ 가짜 서버 시험 미실시)에는 해당하지 않으므로 신 브랜더의 10-10 일정은 그대로여야 한다. 단, 의장이 LAB 에 올리고 시험 주문으로 확인하기 전까지는 "고쳤다"이지 "LAB 에서 고쳐졌다"가 아니다.

### 팀원에게 한마디
신 브랜더에게 — 대본에 "접수 실패" 쪽 문구를 쓸 때, 서버가 대답하지 못한 상태가 있다는 것을 알아 두세요. 화면은 답이 없을 때 "실패"가 아니라 **"접수됐는지 아직 확인하지 못했습니다"** 라고 말하고, 접수번호를 받기 전에는 접수됐다고 하지 않습니다. 오늘 의장의 시험 주문에서 저장은 됐는데 손님에게 실패로 보인 일이 있었습니다. 그래서 대화형 화면의 문구도 "안 됐다 / 됐다 / 모른다" 세 가지가 필요합니다. "모른다" 때 손님이 할 일("다시 확인 / 카톡 문의")을 대본 말투로 한 번 써 봐 주시면 제가 10-11 에 그 문구를 그대로 옮길게요. 오늘 쓴 문구(`app/app.js` 의 `UNKNOWN_TEXT`)는 딱딱한 편이라 말투는 신 브랜더가 다듬어 주면 좋겠습니다.
