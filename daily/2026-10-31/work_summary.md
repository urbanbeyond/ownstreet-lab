## 오늘 한 것
`CLAUDE.md`, `daily/2026-10-31/pm_decision.md`, `app/COMPONENTS.md` 를 먼저 읽고 오늘 목표(뒷면
목업 사이즈별 비율 + 10-27 수정 반영 뒤 "신청자명" 라벨과 목업 카드가 이어 붙었을 때 겹침·위계
문제 재점검)를 확인했다.

1. **코드 추적**: `app/app.js`의 `buildMockupCard(size)`(831행)와 `app/styles.css`의
   `.mockup-img`(392행)를 읽었다. `tee-back-mockup.svg`는 `viewBox="0 0 581 534"`로 고정된
   단일 SVG(사진 1장 + 점선 프린트 영역)이고, `<img>` 태그도 `width=581 height=534` 고정값 +
   CSS `width:200px; max-width:70%; height:auto`로 렌더링된다. `size` 매개변수는 그림 자체에는
   전혀 쓰이지 않고 카드 하단 안내 문구(`"M 사이즈 · 뒷면 단일 프린트 · 최대 A3 사이즈"`)에만
   들어간다 — 즉 사이즈별로 다른 비율/스케일을 적용하는 로직은 **처음부터 없다**. 하나의
   그림을 모든 사이즈가 공유하는 구조.
2. **Playwright 실측(10-27/10-28과 같은 방식)**: Playwright(1.64.1, `/tmp/pw`에 설치, 저장소에
   흔적 없음)로 `app/`을 `python3 -m http.server`로 띄우고, `vendor/firebase-12.19.0.js`를
   `page.route()`로 가짜 모듈로(`signInWithPopup`이 즉시 가짜 사용자 `qa.tester@example.com`을
   돌려줌), 접수 서버(`script.google.com`) 요청도 `page.route()`로 가로채 가짜 접수번호
   `OS-0099`로 응답하도록 모의했다. 실제 Google 계정, 실제 Apps Script 서버에는 어떤 요청도
   가지 않았다. 입력값은 전부 가짜(홍길동·010-1234-5678·서울시 강남구 테스트로 등).
   - S/M/L/XL/2XL/3XL 6개 사이즈 × 모바일(375×812)/데스크톱(1280×900) 2개 폭 = 12개 조합을
     "주문 시작" → 이미지 링크 → 한 줄 이야기(건너뛰기) → 사이즈 선택 → 로그인 → 이름 →
     전화번호 → 주소 → 배송 요청(건너뛰기) → 확인 카드 동의·주문하기 → 접수 완료까지 전부
     끝까지 밟았다.
   - 매 조합에서 `.done-card`, `.mockup-card`, `.mockup-img`의 `boundingBox()`를 재서 두 카드
     사이 겹침 여부(`doneBox.bottom > mockupBox.top`)와 간격, 이미지 크기를 수치로 기록했다.
   - 애니메이션 도중 캡처는 속을 수 있다는 10-25/10-28의 교훈을 따라 완료 카드가 뜬 뒤 800ms,
     스크롤 뒤에는 600ms씩 대기 후 측정·캡처했다.
3. **결과**: 12개 조합 전부 `overlap: false`, `.done-card`와 `.mockup-card` 사이 간격 10px로
   일정. `.mockup-img`의 `boundingBox`가 12개 조합 모두 완전히 동일(`width:200, height:183.8`)
   — 설계상 "모든 사이즈가 같은 비율로 보이는지"에 대한 답은 "그렇다"이지만, 그 이유는 사이즈별
   계산이 맞아서가 아니라 애초에 사이즈에 무관한 고정 이미지 하나를 재사용하기 때문이다.
   fullPage 스크린샷에서 처음엔 상단 `OWN STREET` 바가 중간에 또 보여 레이아웃 버그처럼
   보였는데, `.topbar-wrap`이 `position: sticky`라 Playwright `fullPage` 캡처(스크롤하며 이어
   붙이는 방식)의 흔한 아티팩트였다 — 실제 사용자가 보는 뷰포트만(스크롤해서 캡처) 다시
   찍어보니 문제없음을 확인했다(`scrollIntoViewIfNeeded()` 뒤 뷰포트 캡처).
4. **"신청자명" 라벨 교차 확인**: 확인 카드(`.order-card`)의 "신청자명" 행을
   `boundingBox()`와 `Range.getClientRects().length`로 재측정 — height 20px, rect 1개로 다른
   1줄 행과 완전히 일치. 10-27에 고친 축약(`"신청자명(입금자명)"` → `"신청자명"`)이 그대로
   유지되고 있음을 재확인했다. (주의: 이 라벨은 `.order-card`에 있고, 목업 카드는 `.done-card`
   다음에 붙는다. 둘은 같은 화면 흐름의 서로 다른 단계 카드다 — "확인 카드 바로 다음에 목업
   카드"가 아니라 "확인 카드 제출 → 완료 카드 → 목업 카드" 순서. pm_decision 이 말한 "이어
   붙었을 때"를 접수 완료 이후 전체 흐름으로 해석해 `.order-card`와 `.done-card`+`.mockup-card`
   양쪽을 모두 점검했다.)

## 검증에 쓴 방법 (서버·실제 계정 접근 없음)
- `app/`을 `python3 -m http.server`로 로컬에 띄우고 Playwright(chromium, `/tmp/pw`에 임시
  설치, 저장소에 흔적 없음)로 접속.
- Firebase 로그인은 `page.route()`로 `vendor/firebase-12.19.0.js`를 테스트 전용 가짜 모듈로
  바꿔치기(실제 Google 계정과 통신 없음).
- 접수 서버(`requestEndpoint`)로 가는 실제 요청은 전부 `page.route()`로 가로채 모의 응답만
  돌려줬다(GET: `{ready:true, version:2}`, POST: `{ok:true, request_id:'OS-0099', v:2}`). 실제
  Apps Script 서버에는 어떤 요청도 가지 않았다. 입력한 이름/전화번호/주소는 전부 가짜 값.
- `config.js`의 `requestEndpoint`·`firebase`·`payment.kakaopayLink`·`contactUrl`,
  `kakaopay-qr.svg`는 전혀 건드리지 않았다.

## 잘 안 된 것, 아쉬운 것
- 새로운 버그는 찾지 못했다. "문제가 없으면 코드를 건드리지 않는다"는 지시대로 오늘은 관찰로
  끝났다 — 10-28 developer가 남긴 것과 비슷하게, 이미 10-27에 한 번 고쳐진 부분을 다시 두껍게
  확인한 날에 가깝다.
- fullPage 스크린샷에서 sticky 헤더가 중복으로 보이는 현상 때문에 처음엔 레이아웃 버그로
  오인할 뻔했다. 다음에 비슷한 QA를 할 팀원은 `fullPage: true` 캡처에서 sticky 요소가 여러 번
  보이면 먼저 "캡처 방식의 문제인지"부터 의심하고, 실제 뷰포트만 스크롤해서 다시 찍어 보는
  것을 권한다(오늘 `scrollIntoViewIfNeeded()` 사용).
- "사이즈별로 같은 비율로 보이는지"를 다른 방식(예: 사이즈별 실루엣 크기를 다르게 그리는 것)이
  더 정확한 표현일 수 있는지는 오늘 판단 범위에 넣지 않았다. 지금 설계(고정 이미지 + 안내
  문구로만 사이즈 구분)는 COMPONENTS.md에도 "실제 상품(피그먼트 차콜 반팔) 뒷면 사진"이라고
  명시돼 있고, 의장 요청(R-023)으로 확정된 방향이라 디자이너 권한으로 바꿀 사안이 아니라고
  판단했다.
