## 오늘 한 것
PM 목표대로 세 번(10-15 developer 본인, 10-16·10-18 designer) 밀린 "시험·수정"을 했다.
`app/app.js`·`app/index.html`·`app/styles.css`를 다시 읽고, 코드 레벨 점검 + Playwright(이미

Google 로그인은 사람만 할 수 있어 실제 네트워크 요청(로그인, 접수 서버)은 전혀 보내지 않았고,
모든 확인은 정적 렌더링 + UA 시뮬레이션으로 했다.

### 1) 모바일 폭(375px) 렌더링 — 실제 버그 발견, 고쳤다
"주문 시작"부터 이미지 링크 → 한 줄 이야기(건너뛰기) → 사이즈 선택까지 실제로 버튼을 눌러가며
진행해 보니, **"한 줄 이야기" 질문 말풍선과 그다음 사이즈 선택 칩이 같은 화면에서 겹쳐 보였다.**
데스크톱 1280px에서도 똑같이 재현됐다 — 모바일만의 문제가 아니었다.

원인을 DOM 좌표(`bounding_box()`)로 추적한 결과:
- 새 메시지가 추가될 때 화면을 따라 내려가게 하는 `keepInView()`가 `$('chatInput').scrollIntoView(...)`
  를 쓰고 있었다. 그런데 `#chatInput`은 `position: sticky; bottom: 0`이라 브라우저가 "뷰포트 안에
  항상 보이는 요소"로 취급해서 `scrollIntoView`를 걸어도 **스크롤이 전혀 일어나지 않았다**
  (`window.scrollY`가 계속 0으로 고정되는 것을 직접 확인했다. 같은 상황에서 `#chatLog`의 마지막
  `li`로 스크롤을 걸면 정상적으로 스크롤됐다 — sticky 요소 자체가 원인임을 교차 확인).
- 그 결과 `.chat-log`가 뷰포트보다 길어져도 화면이 안 내려가서, sticky로 바닥에 눌러앉은 입력창이
  아직 다 보이지도 않은 이전 질문·답변 말풍선 위에 그대로 겹쳐 떠 있었다.

고친 내용:
- `keepInView()`가 `#chatInput` 대신 `#chatLog`의 마지막 메시지(`lastElementChild`)를 스크롤
  타겟으로 삼도록 바꿨다(`block: 'end'`). sticky 요소를 피해서 스크롤이 실제로 일어나게 했다.
- 이것만으로는 `scrollIntoView(block:'end')`가 메시지를 뷰포트 끝에 딱 맞춰 버려서 sticky 입력창
  (최대 약 106px 높이, 사이즈 2줄 조합이면 더 큼)에 메시지 아랫부분이 약 19px 가려지는 잔여 겹침이
  남았다. `.msg`에 `scroll-margin-bottom: 140px`을 줘서 입력창 높이만큼 여유를 두고 해결했다.
- 수정 후 Playwright로 전수 검사(모든 `<li>`의 bounding box와 `#chatInput`의 bounding box가
  겹치는지)를 모바일 375px·데스크톱 1280px 양쪽에서 다시 돌려 **겹침 0건**을 확인했다. 스크린샷으로도
  확인(아래 바뀐 파일에는 안 올렸다 — 가짜 URL/임시 텍스트만 쓴 디버그용 스크린샷이라 저장소에
  남기지 않았다, designer 10-18 관례와 같음).

### 2) 중복 접수 방어 — 버그 없음, 재확인만 했다
PM이 요청한 범위대로 **클라이언트 쪽 재전송 트리거**를 점검했다(서버 쪽 clientRef 중복 찾기는
`backend/Code.gs`의 `findByClientRef_`가 이미 맡고 있고, 오늘은 손대지 않았다).
- `submitOrder()`는 현재 답변 내용으로 만든 서명(`sig`)이 이전 `state.pending.sig`와 같으면 새
  `clientRef`를 만들지 않고 **기존 pending을 그대로 재사용**한다(`app.js` 575번째 줄 근처).
- 실패 후 뜨는 "다시 시도" 버튼(`handleResult`)과 "다시 확인" 버튼(`unknownChoices`)은 둘 다
  `submitOrder()`/`recheckPending()`을 다시 부를 뿐, 직접 `newClientRef()`를 호출하지 않는다.
  즉 같은 내용으로 몇 번을 눌러도 서버에는 같은 `clientRef`로만 간다.
- 내용을 고친 뒤(`sig`가 달라진 뒤) 다시 보낼 때만 `settleOldPending()`으로 이전 요청의 저장 여부를
  먼저 확인하고, 확실히 "저장 안 됨"인 경우에만 새 `clientRef`를 만든다 — 저장됐을 수도 있는
  상태에서는 새로 만들지 않는다.
- 결론: 클라이언트 쪽 중복 접수 방어 로직은 설계대로 동작하고 있고, 버그를 찾지 못했다.

### 3) 인앱 브라우저(카카오톡·인스타그램) 안내 — 버그 없음, 재확인만 했다
실제 카카오톡/인스타그램 User-Agent 문자열(Android·iOS)로 페이지를 열어서 확인했다.
- 카카오톡(Android, iOS) 둘 다 `isInAppBrowser()`가 true로 잡혀 "앱 안 브라우저에서는 주문할 수
  없습니다. Chrome이나 Safari에서 열어주세요." 안내와 "브라우저로 열기"/"주소 복사" 버튼이 정확히
  나왔다.
- 인스타그램(iOS UA)은 `inAppKind()`가 `other`로 떨어져(코드 의도: iOS 인앱은 자동으로 열 방법이
  없음) "···또는 공유 버튼을 누르고 Safari로 열기" 안내 문구가 추가로 나오고 "주소 복사"만 제공됐다
  — 코드 설계 그대로 동작.
- 일반 Chrome(Android)·Safari(iOS) UA에서는 인앱 안내 없이 정상적으로 "주문 시작" 버튼이 나왔다.
- `openExternalBrowser()`의 카카오(`kakaotalk://web/openExternal?url=`), 라인 scheme도 코드만
  읽고 구조를 확인했다(실제로 location.href를 바꾸는 호출이라 클릭 테스트는 하지 않았다).
- 결론: 인앱 브라우저 감지·안내는 지금 코드에 그대로 살아 있고 조건도 올바르다. 고칠 것 없음.
