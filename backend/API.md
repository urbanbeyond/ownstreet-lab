# OWN STREET 접수 서버 API (Code.gs v2)

화면(`app/`)과 접수 서버(`backend/Code.gs`, Google Apps Script)가 주고받는 데이터 형식이다.
서버 코드를 바꾸면 이 문서도 같이 바꾼다. 서버 배포는 의장이 한다 (`OPERATOR_TODO.md`).

- 서버 주소는 `app/config.js` 의 `requestEndpoint` (`.../exec`). 이 문서에는 쓰지 않는다.
- 이 문서의 예시 값은 전부 지어낸 값이다. 실제 고객 정보, 토큰, 스프레드시트 ID 는 어디에도 쓰지 않는다.
- 모의 테스트: `node backend/test/code-gs.test.js` (실제 서버가 아니라 Apps Script 를 흉내 낸 가짜 환경에서 도는 테스트다).

## 1. 상태 확인 — `GET <exec 주소>`

브라우저 주소창에 열면 된다. 저장 기능이 없고, 고객 데이터를 읽지 않는다.

```json
{
  "ok": true,
  "service": "OWN STREET",
  "version": 2,
  "ready": true,
  "storage": true,
  "message": "접수 서버가 작동 중입니다."
}
```

| 필드 | 뜻 |
|---|---|
| `version` | 서버 버전. **2 이상**이어야 대화형 주문 화면이 접수를 시도한다. 필드가 없으면 v0 서버(옛 코드)다. |
| `storage` | 저장할 스프레드시트를 열 수 있는지. `false` 면 스크립트 속성 `SPREADSHEET_ID` 를 확인한다. |
| `ready` | 로그인 확인 키(`FIREBASE_API_KEY`)와 저장 시트가 모두 준비되었는지. `false` 면 접수를 받지 못한다. |
| `message` | 사람이 읽는 한 줄. `ready` 가 `false` 인 이유가 여기 나온다. |

## 2. 접수 요청 — `POST <exec 주소>`

- 본문은 JSON 문자열. `Content-Type: text/plain;charset=utf-8` 로 보낸다 (Apps Script 가 브라우저에 응답을 그대로 돌려주는 방식).
- 요청 형식은 `v` 로 구분한다. **`v` 가 없으면 옛 형식(v0 폼), `v: 2` 면 새 형식**이다.

### 2-1. 옛 형식 (`v` 없음) — v0 화면이 지금 보내는 것

```json
{
  "action": "request",
  "idToken": "<Firebase 로그인 토큰>",
  "name": "홍길동",
  "phone": "010-0000-0000",
  "url": "https://example.test/share/abc",
  "consent": true,
  "clientRef": "ref-k3j9x0a1-abcd"
}
```

`name`, `phone`, `url`, `consent` 필수. `clientRef` 는 있으면 중복 접수를 막는 데 쓴다.
(이 형식에 `size`, `address`, `memo`, `story` 가 따라오면 **있는 것은 검증해서 저장**한다. 틀리면 거절한다.)

### 2-2. 새 형식 (`v: 2`) — 대화형 화면이 보낼 것

```json
{
  "action": "request",
  "v": 2,
  "idToken": "<Firebase 로그인 토큰>",
  "name": "홍길동",
  "phone": "010-0000-0000",
  "url": "https://example.test/share/abc",
  "size": "L",
  "address": "테스트시 예시구 가상로 1, 101동 101호",
  "memo": "문 앞에 두세요",
  "story": "이 그림은 내가 처음으로 정한 나의 색이다",
  "consent": true,
  "clientRef": "ref-k3j9x0a1-abcd"
}
```

### 2-3. 항목별 규칙

| 항목 | 옛 형식 | v2 | 규칙 |
|---|---|---|---|
| `action` | 필수 | 필수 | 정확히 `"request"` |
| `v` | 없음 | 필수 | 없음 또는 `1` = 옛 형식, `2` = 새 형식. 숫자여야 한다 (`"2"` 글자는 `BAD_REQUEST`). `2` 보다 크면 `VERSION_MISMATCH`. |
| `idToken` | 필수 | 필수 | Firebase 로그인 토큰. 서버가 Google 에 직접 확인한다 (Google 로그인, 이메일 인증됨, 정지 안 됨). |
| `name` | 필수 | 필수 | 1~40자. 제어문자는 지우고 연속 공백은 하나로. |
| `phone` | 필수 | 필수 | 한국 전화번호. 숫자만 뽑아 `010-1234-5678` / `02-123-4567` 모양으로 저장. |
| `url` | 필수 | 필수 | `http(s)://도메인...` 모양, 2000자 이하. **링크가 열리는지, PNG 인지는 확인하지 않는다.** |
| `size` | 없어도 됨 (있으면 검증) | 필수 | 정확히 `S`, `M`, `L`, `XL`, `2XL`, `3XL` 중 하나. 소문자·다른 글자는 거절. 앞뒤 공백만 지운다. |
| `address` | 없어도 됨 (있으면 검증) | 필수 | 5~200자. 줄바꿈은 공백으로. |
| `memo` | 선택 | 선택 | 배송 요청. 0~300자. 비우거나 항목을 빼도 된다. |
| `story` | 선택 | 선택 | 한 줄 이야기(손님이 직접 쓴 한 줄). 0~200자. 비우거나 항목을 빼도 된다. |
| `consent` | 필수 | 필수 | 정확히 `true` (불리언). 아니면 `CONSENT_REQUIRED`. |
| `clientRef` | 선택 | 필수 | 영문·숫자·`-` 로 8~64자. **같은 주문을 다시 보낼 때는 같은 값, 내용이 바뀌면 새 값.** |

- 자유 입력(`name`, `address`, `memo`, `story`, `url`)이 `=`, `+`, `-`, `@` 로 시작하면 시트에서 수식으로 읽히지 않도록 앞에 `'` 를 붙여 저장한다 (`safeCell_`).
- 글자 수는 정리(공백 정리)한 뒤의 글자 수다. 길이 한도는 `Code.gs` 위쪽 상수(`ADDRESS_MAX`, `MEMO_MAX`, `STORY_MAX`)에 있다. `story` 200자는 대본이 나오기 전의 임시 값이다.
- 사이즈 목록은 `app/config.js` 의 `sizeTable.rows` 와 `Code.gs` 의 `SIZES` 두 곳에 있다. 사이즈를 바꾸면 두 곳을 같이 고친다.

### 2-4. 확인 순서

서버는 아래 순서로 확인하고, 처음 걸린 것에서 멈춘다.
`action` → `v` → 서버 설정(`FIREBASE_API_KEY`) → **로그인 토큰** → 입력값(모든 틀린 항목을 한 번에 모아서) → `consent` → 잠금 → (중복 확인) → 저장 → **다시 읽어 확인** → 응답.

## 3. 응답

항상 JSON. 성공일 때만 `request_id` 가 들어 있다. **`request_id` 는 서버가 저장한 줄을 다시 읽어 확인한 뒤에만 만들어진다.**

### 3-1. 성공

```json
{ "ok": true, "v": 2, "request_id": "OS-0001", "created_at": "2026-10-09 12:00:00" }
```

같은 사람이 같은 `clientRef` 로 다시 보냈고 이미 저장된 줄이 있으면, 새 줄을 만들지 않고 그 줄의 번호를 돌려준다.

```json
{ "ok": true, "v": 2, "request_id": "OS-0001", "created_at": "2026-10-09 12:00:00", "duplicate": true }
```

**화면이 완료로 인정하는 조건** (이 중 하나라도 아니면 실패로 보여 준다):
1. `ok === true`
2. `request_id` 가 `OS-숫자` 모양
3. 새 화면(v2 요청)은 추가로 `v >= 2` — 옛 서버가 모르는 항목을 조용히 버리고 성공을 돌려주는 일을 막는 증거다.

### 3-2. 실패 (`ok: false`)

| `code` | 뜻 | 화면이 할 일 |
|---|---|---|
| `BAD_REQUEST` | JSON 이 아니거나 `action`/`v` 가 이상함 | 일반 실패 안내 |
| `VERSION_MISMATCH` | 서버가 모르는 더 새로운 `v` | "주문을 준비하고 있습니다" 안내. 서버 배포가 필요하다는 뜻 |
| `NOT_CONFIGURED` | 서버 설정(API 키 등)이 안 됨 | "주문을 준비하고 있습니다" 안내 |
| `AUTH_INVALID` | 로그인 토큰이 잘못됐거나 만료됨 | 토큰을 새로 받아 한 번 더, 그래도 안 되면 다시 로그인 |
| `AUTH_UNAVAILABLE` | Google 로그인 확인 서버에 연결하지 못함 | 잠시 후 다시 시도 |
| `INVALID_INPUT` | 입력값이 틀림. `fields` 에 틀린 항목 이름 배열 (예: `["size","address"]`) | 해당 질문으로 돌아가기 |
| `CONSENT_REQUIRED` | `consent` 가 `true` 가 아님 | 동의 체크 안내 |
| `BUSY` | 다른 접수 처리 중이라 30초 안에 차례가 안 옴 | 잠시 후 다시 시도 (같은 `clientRef` 로) |
| `SERVER_ERROR` | 저장하지 못했거나, **저장을 다시 읽어 확인하지 못함**, 시트를 열 수 없음 등 | 일반 실패 안내 + 다시 시도 (같은 `clientRef` 로) |

- `SERVER_ERROR` 뒤에 같은 `clientRef` 로 다시 보내도 안전하다. 줄이 이미 써졌다면 그 줄의 번호를 돌려주고, 안 써졌다면 새로 쓴다.
- 실패 응답에는 `request_id` 가 없다. 화면은 실패 응답에서 번호를 만들지 않는다.
- 네트워크 끊김·시간 초과(`NETWORK`, `TIMEOUT`)와 해석할 수 없는 응답(`BAD_RESPONSE`, `HTTP_*`)은 서버의 답이 아니라 화면이 알아차리는 **"답 없음"** 이다. 이 경우 서버가 이미 저장했을 수 있으므로 화면은 **"실패"라고 단정하지 않는다.** 같은 `clientRef` 로 다시 보내 확인하고(이미 저장돼 있으면 `duplicate: true` 와 같은 번호가 돌아온다), 끝내 확인하지 못하면 "접수됐는지 확인하지 못했다"고 사실대로 말한다. (2026-10-08 LAB 시험: 서버가 37.853초 걸려 저장까지 마쳤는데 화면이 30초에서 끊고 "실패"를 보여 줬다.)
- 화면의 한 번 기다리는 한도는 60초다 (`app/app.js` 의 `REQUEST_TIMEOUT_MS`). 서버가 잠금을 기다리는 시간만 최대 30초이고 저장 시간이 따로 붙는다.
- 서버가 저장 전에 끝내는 응답(저장 안 됨이 분명한 것): `BAD_REQUEST`, `VERSION_MISMATCH`, `NOT_CONFIGURED`, `AUTH_INVALID`, `AUTH_UNAVAILABLE`, `INVALID_INPUT`, `CONSENT_REQUIRED`, `BUSY`. `SERVER_ERROR` 는 저장 뒤 다시 읽기 확인에서 날 수도 있으므로 저장 여부가 불분명할 수 있다.

## 4. 시트 `REQUESTS` — 열 순서

열은 **앞에서부터 늘어난다. 이미 있는 열의 순서는 바꾸지 않는다.** 새 열은 항상 맨 뒤에 덧붙인다.

| 열 | 머리글 | 들어가는 값 | 처음 생긴 버전 |
|---|---|---|---|
| A (1) | 접수번호 | `OS-0001` … | v0 |
| B (2) | 접수시간 | `yyyy-MM-dd HH:mm:ss` (서울 시간) | v0 |
| C (3) | 이메일 | Google 계정 이메일 (서버가 토큰으로 확인한 값, 소문자) | v0 |
| D (4) | 이름 | | v0 |
| E (5) | 전화번호 | | v0 |
| F (6) | URL | | v0 |
| G (7) | 상태 | 새 줄은 `접수` | v0 |
| H (8) | 사이즈 | `S`~`3XL`. 옛 형식 요청이면 비어 있음 | v2 |
| I (9) | 주소 | 옛 형식 요청이면 비어 있음 | v2 |
| J (10) | 배송 요청 | `memo`. 없으면 비어 있음 | v2 |
| K (11) | 한 줄 이야기 | `story`. 없으면 비어 있음 | v2 |
| L (12) | clientRef | 중복 접수를 찾는 데 쓰는 값 | v2 |
| M (13) | 동의 시각 | `consent: true` 가 담긴 요청을 서버가 받은 시각 (현재는 접수시간과 같은 순간) | v2 |

머리글 처리 (`ensureHeaders_`):
- 시트가 비어 있으면 13칸 머리글을 모두 쓴다.
- 이미 머리글이 있는 시트는 **비어 있는 칸만** 채운다. 1~7번 칸의 이름이 달라도(의장이 바꿔 뒀어도) 덮어쓰지 않는다. 약속은 이름이 아니라 **열의 위치**다.
- 8~13번 칸에 이미 다른 글자가 있으면 덮어쓰지 않고 **접수를 멈춘다** (`SERVER_ERROR`, 서버 로그에 "머리글 충돌"). 사람의 데이터를 덮어쓰는 것보다 접수가 멈추는 쪽이 낫다고 보았다.
- 시트 열 개수가 13개보다 적으면 열을 늘린다.
- 동의 문구의 "버전"(어떤 문구에 동의했는지)은 아직 저장하지 않는다.

## 5. 저장소(스프레드시트) 설정

- 스프레드시트 ID 는 **코드에 쓰지 않는다.** Apps Script 의 스크립트 속성 `SPREADSHEET_ID` 에서 읽는다 (⚙ 프로젝트 설정 → 스크립트 속성).
- 속성이 없으면, 스크립트가 스프레드시트에 붙어 있을 때(확장 프로그램 → Apps Script)만 그 시트를 쓴다.
- 속성이 있는데 그 시트를 열 수 없으면 붙어 있는 시트로 **몰래 바꾸지 않고** 접수를 실패시킨다 (엉뚱한 시트에 고객 정보가 쌓이는 것을 막기 위해).
- `OS_LAST_SEQ` 속성(마지막 접수번호)은 서버가 자동으로 관리한다. 번호는 `max(OS_LAST_SEQ, 시트의 가장 큰 번호) + 1`.
- `FIREBASE_API_KEY` 는 코드에 있다. config.js 에도 공개되는 Firebase 웹 키이며 비밀값이 아니다.

## 6. 지키는 약속 (서버가 약하게 만들면 안 되는 것)

1. 접수번호는 시트에 쓴 줄을 **다시 읽어서** (접수번호, 이메일, 사이즈, clientRef, 동의 시각이 맞는지, 즉 줄의 맨 끝 칸까지 써졌는지) 확인한 뒤에만 돌려준다.
2. 읽기 확인에 실패하면 `request_id` 없이 `SERVER_ERROR` 를 돌려준다. 가짜 성공도, 임의 번호도 없다.
3. 중복은 시트에 저장된 `clientRef` + 이메일로 찾는다 (캐시에 의존하지 않는다). 다른 사람이 같은 `clientRef` 를 써도 남의 번호를 돌려주지 않는다.
4. 서버가 모르는 요청 형식(`v` 가 더 큼)은 받지 않는다. 항목을 조용히 버리고 성공하지 않는다.
5. 옛 형식 요청(`v` 없음)은 계속 받는다.

## 6-1. 실행 로그 (느린 요청의 원인을 찾기 위한 기록)

접수 요청 하나가 끝날 때마다 Apps Script 실행 기록(로그)에 한 줄이 남는다. 동작과 응답은 바뀌지 않는다.

```
[타이밍] 결과=ok OS-0001 | 합계 1234ms | 로그인확인 800ms | 입력확인 0ms | 잠금대기 3ms | 시트열기+머리글 250ms | 중복찾기 20ms | 번호계산 30ms | 쓰기 90ms | 다시읽기 40ms | 번호기록 1ms | 시트 줄 수 12
```

- 결과: `ok OS-숫자`, `ok OS-숫자 (duplicate)`, 실패 코드(`AUTH_INVALID`, `BUSY` …), 예외면 `EXCEPTION`(그 뒤의 단계는 없고, 자세한 오류는 같은 실행의 오류 로그에 따로 남는다).
- 단계는 도달한 곳까지만 나온다. 각 시간은 직전 단계 이후 걸린 시간이다.
- 이메일, 이름, 전화번호, 주소, 토큰, 시트 ID, clientRef 는 이 로그에 남기지 않는다.
- 이 로그는 "다음에 느린 요청이 생겼을 때 어느 단계가 길었는지" 보기 위한 것이다. 지금까지 느렸던 이유는 아직 모른다.

## 7. 아직 하지 않는 것 (한계)

- 읽기 확인은 줄의 일부 칸(번호·이메일·사이즈·clientRef·동의 시각)만 비교한다. 이름·주소 같은 자유 입력은 `'` 접두 처리 때문에 값을 그대로 비교하지 않는다. 줄이 맨 끝 칸까지 써졌다는 것으로 갈음한다.
- 같은 `clientRef` 로 **내용이 다른** 요청이 오면 서버는 같은 요청으로 보고 먼저 저장된 번호를 돌려준다. 내용이 바뀌면 새 `clientRef` 를 만드는 것은 화면의 몫이다.
- 읽기 확인에 실패했지만 줄은 시트에 남은 경우, 손님이 다시 시도하지 않으면 그 줄은 시트에 `접수` 상태로 남는다. 의장이 시트에서 번호가 이어지지 않거나 손님이 모르는 줄을 보면 이 경우일 수 있다.
- URL 이 열리는지, PNG 인지는 확인하지 않는다 (방법이 없다).
- 내 주문 조회(`myOrders`), 상태 변경, 이탈 기록은 아직 없다.
